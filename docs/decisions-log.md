# Журнал решений

Коротко: что решили и почему именно так, а не иначе. Основа для раздела README «Технологии и решения».

## Стек и инфраструктура

- **Next.js (App Router) + TypeScript** — фронтенд и бэкенд в одном проекте: один запуск и один деплой. App Router — актуальный подход Next.js с серверными компонентами.
- **Route Handlers (API внутри Next.js) вместо отдельного сервера** — бэкенду нужна одна задача (проверка ответов), отдельный сервис был бы избыточен.
- **Tailwind CSS** — стили пишутся прямо в разметке, без отдельных CSS-файлов на каждый компонент; быстрее всего для небольшого проекта. Выбор подтверждён на шаге дизайна: отдельно изучать другие подходы к CSS (CSS-модули, обычный CSS) ради этого проекта нет смысла.
- **`.gitattributes` с `text=auto`** — в репозитории LF, на машине разработчика окончания строк по его ОС (CRLF на Windows, LF на macOS).

## Контент

- **Статьи в MDX** — текст остаётся обычным Markdown, а упражнение вставляется в любое место одной строкой `<Exercise id="..." />`. Альтернативы хуже: статьи на TSX неудобно редактировать как текст, хранение статей в JSON требует отдельного «рисовальщика» и неудобно для длинных текстов.
- **Единый банк вопросов** — каждый вопрос описан один раз и используется и в статье, и в итоговом тесте.

## Архитектура упражнений

- **Композиция «оболочка + начинка» вместо наследования** — общая оболочка (`ExerciseShell`) и общий хук (`useExercise`) отвечают за состояния, проверку и обратную связь; каждый тип реализует только свой способ ввода ответа. Один большой компонент с `switch` по типам разросся бы, полностью независимые компоненты дублировали бы логику.
- **Тестовый режим через React Context** — упражнение само определяет режим: внутри теста отправляет результат в общий контекст, в статье работает автономно. Альтернатива — передавать колбэк `onResult` каждому вопросу — тоже рабочая, но контекст удобнее, когда счёт и прогресс нужны сразу в нескольких местах (прогресс-бар, вопросы, сводка).
- **Состояние теста на `useReducer`, счёт вычисляется из результатов** — хранится только список результатов, а баллы и прогресс считаются из него; нет риска, что счёт разойдётся с ответами.

## Проверка ответов

- **Проверка на сервере (POST `/api/check`)** — правильные ответы и объяснения не попадают в браузер до раскрытия (когда и как ответ раскрывается — см. раздел «Обратная связь»), их нельзя подсмотреть в коде страницы. Цена — небольшая задержка и состояние «проверяю…».
- **Осознанно не закрыто: перебор ответов через API** — сервер проверки ничего не запоминает, поэтому ответ можно подобрать, отправляя варианты по очереди, а счёт теста считается в браузере. Закрывать не стали: у портала нет оценок, рейтингов и сертификатов, это тренажёр — кто перебирает ответы, обманывает только себя. Как закрыть, если понадобится честный зачёт: хранить попытки прохождения в базе данных, принимать один ответ на вопрос в рамках попытки и считать итоговый балл на сервере. Ограничение частоты запросов не решает проблему, а лишь замедляет перебор.
- **Банк вопросов помечен `server-only`** — если случайно импортировать его в браузерный код, сборка упадёт.
- **Вопросы страницы получают напрямую, без GET-эндпоинта** — серверные компоненты читают банк сами и передают в браузер только публичную часть. Запрос к собственному API из серверного компонента — лишний сетевой круг, а при статической сборке он вообще не работает.
- **Валидация запросов через zod** — схема описывает ожидаемый формат ответа и одновременно даёт TypeScript-тип.
- **Сервер не доверяет присланному ответу** — интерфейс не даёт отправить неполный ответ, но запрос к API можно отправить и в обход страницы (из инструментов разработчика или программой). Поэтому сервер проверяет, что ответ подходит именно этому упражнению: все утверждения, пропуски, пары или шаги на месте, без повторов и посторонних id. Иначе — ошибка 400, и балл не считается: иначе можно было бы, например, получить «верно» за неполный список.
- **Безопасность пользовательского ввода** — введённый текст выводится только React-ом как обычный текст (React сам экранирует его, поэтому вставленный HTML или скрипт не выполнится); `dangerouslySetInnerHTML` с пользовательскими данными не используется. Сервер ввод не хранит и не возвращает в ответе — только сравнивает с допустимыми ответами; размеры и формат ограничены схемой zod. Правила на будущее, когда появятся база данных и данные, видимые другим пользователям: запросы к базе — только параметризованные: через построитель запросов или ORM (например, Kysely, Drizzle, Prisma), никакой склейки строк и никаких пользовательских данных в «сыром» SQL (`sql.raw` и аналоги) — защита от SQL-инъекций, пользовательский текст — только как текст, проверка ввода — на сервере.

## Оценка ответов

- **Балл — доля правильно выполненных элементов ответа (от 0 до 1)** — найденные верные варианты, верно соединённые пары, верно заполненные пропуски. Единый принцип для всех типов упражнений; тест просто складывает баллы. Для упражнения на порядок шагов правило будет выбрано отдельно — там «элемент» можно понимать по-разному.
- **Три итога: «Верно» (1), «Частично верно» (между 0 и 1), «Неверно» (0)** — итог должен совпадать с начисленным баллом: если за ответ «2 из 3» начисляется 0,67, писать «Неверно» было бы противоречием. Кроме того, «частично верно» подсказывает, что делать дальше — искать упущенное, а не пересматривать подход целиком.
- **Вопросы с несколькими верными ответами: «выберите все подходящие» с невидимым лимитом** — отметить можно не больше вариантов, чем верных (N), но само N заранее не показывается; подсказка «Можно выбрать не больше N вариантов» появляется, только если упереться в лимит. Балл = найдено / N. Так стратегия «отметить всё» невозможна на уровне интерфейса, и штрафы не нужны. Пользователь при этом сам решает, сколько вариантов верны, — это ценнее для обучения, чем готовое «выберите три». Рассмотренные альтернативы: «всё или ничего» не отличает «почти верно» от «совсем мимо»; формулы со штрафом за лишние варианты либо слишком строги (один лишний обнуляет всё), либо сложны для объяснения пользователю; шкала по числу ошибок (как в ЕГЭ) награждает «отметить всё», если неверный вариант всего один; поштучная оценка вариантов даёт много баллов за «отметить всё», когда верных большинство.

## Обратная связь

- **В статье — ступенчато** — после первой проверки показываются итог и подсказка, которая помогает найти ошибку, но не называет ответ (например, «Найдено 2 из 3 верных вариантов»). Дальше на выбор: «Попробовать ещё раз» или «Показать ответ» — отметки у верно выбранных, лишних и пропущенных вариантов и объяснение. Неотмеченные неверные варианты остаются без отметки: отмечается только то, на что стоит обратить внимание, иначе разбор превращается в шум. При верном ответе объяснение показывается сразу. После верного ответа и после «Показать ответ» кнопок повтора нет: ответ уже известен, повторять нечего. Почему не «всё сразу»: объяснение фактически называет ответ, и повторная попытка после него теряет смысл; ступенчатая схема даёт подумать ещё раз, но не заставляет мучиться.
- **В тесте — полная обратная связь сразу после каждого вопроса** — повтора в тесте нет, поэтому прятать ответ незачем, а немедленная обратная связь лучше для обучения, чем разбор только в конце. Итоговая сводка показывает общий счёт.
- **Раскрытие ответа решает сервер** — в запрос проверки добавлен флаг `reveal`. Правильные ответы, объяснение и разбор по вариантам приходят в браузер, только если ответ верный, если пользователь нажал «Показать ответ» или если это тест. Правило записано в одном месте для всех типов упражнений. «Показать ответ» повторно отправляет тот же ответ — так разбор («лишний», «пропущен») строится относительно того, что выбрал пользователь, и отдельный эндпоинт не нужен.
- **Пояснения к отдельным вариантам — необязательные** — короткий комментарий «почему этот вариант неверный» самая полезная форма обратной связи, но писать его к каждому варианту дорого. Поле необязательное, заполняется там, где ошибка типичная; показывается у лишних и пропущенных вариантов.
- **Итог и разбор обозначаются значком и словом, а не только цветом** — требование стандарта доступности WCAG: часть людей не различает красный и зелёный.

## Дизайн

- **Простой лаконичный стиль** — нейтральная основа (белый фон, серые рамки, один цвет-акцент). Упражнения — заметные карточки, но не «кричат». Нейтральная основа не будет спорить с яркими элементами, если позже появятся иллюстрации или элементы прогресса.
- **Дизайн-токены** — все цвета заданы переменными в одном месте (`app/globals.css`) и подключены к Tailwind как именованные цвета (`bg-surface`, `text-muted`, `bg-accent-fill`…). Компоненты не содержат «зашитых» цветов: тема и палитра меняются правкой одного файла.
- **Светлая тема по умолчанию + переключатель на тёмную** — выбор запоминается в браузере. Чтобы страница не мигала светлой при загрузке, тема выставляется маленьким скриптом в `<head>` до первой отрисовки (приём из руководства Next.js «Preventing flash before hydration»). Тему не берём из системных настроек: по умолчанию сайт задуман светлым. Смена темы — плавное растворение всей страницы целиком (View Transitions API, 0,3 с), без отстающих элементов; если в системе включено «уменьшить движение» или браузер не поддерживает эту технологию — мгновенно, но тоже целиком.
- **Акцент — индиго** — холодный цвет не спорит с цветами итогов (зелёный, янтарный, красный) и с тёплыми иллюстративными элементами, которые могут появиться позже. Зелёный, янтарный и красный используются только для итогов и разбора ответов. Индиго разделён на два токена: светлый — для ссылок, значков и рамок (читается на тёмном фоне), насыщенный — для заливки кнопок с белым текстом. Раньше в тёмной теме кнопки были светло-индиговыми с чёрным текстом: формально контраст проходил стандарт, но на деле читалось тяжело. При наведении в тёмной теме кнопка светлеет, а не темнеет.
- **Типы упражнений различаются значком и названием, а не цветом** — карточка у всех типов одинаковая. Если раскрасить типы, их цвета спорили бы с цветами итогов.
- **Шрифт Geist везде** — единообразно и лаконично; вариант со шрифтом с засечками для текста статей рассмотрен и отклонён.
- **Главная — оглавление курса** — короткое вступление и карточки статей по порядку («шаг 1…4») со значками темы. Значки, а не картинки: они в том же стиле, что и интерфейс, и работают в обеих темах. Значок занимает полосу слева на всю высоту карточки — у оглавления характер «каталога шагов». Для первой статьи выбран курсор: он передаёт её главную мысль — модель предсказывает следующее слово (варианты «мозг», «схема связей», «коробка» рассмотрены; «коробка» ближе к теме контекста и визуально похожа на значок статьи о структуре промпта).
- **Кнопки выглядят как кнопки** — у всех активных кнопок курсор-«рука» (Tailwind 4 по умолчанию оставляет обычную стрелку). Главное действие — заполненная кнопка в цвете акцента («Проверить», «Пройти тест»). «Проверить» никогда не блокируется: если ответ заполнен не полностью, по клику появляется подсказка («Заполните все пропуски», «Оцените все утверждения», «Выберите хотя бы один вариант»), незаполненное подсвечивается индиго и получает фокус — заблокированная кнопка не объясняет, чего не хватает. Второстепенные — кнопки, а не ссылки, и немного различаются: «Попробовать ещё раз» — на мягком индиго-фоне (подталкиваем сначала подумать ещё раз), «Показать ответ» — нейтральная, с рамкой.
- **«Пройти тест» — в шапке на всех страницах; правая часть шапки — место для действий** — сейчас там тест и переключатель темы, позже может появиться индикатор прогресса.
- **Отдельная страница списка статей убрана** — список живёт на главной, адрес `/articles` перенаправляет туда. Редирект временный (307), а не постоянный (308): постоянный браузеры запоминают навсегда, и вернуть страницу потом было бы сложно.
- **Переход по курсу внизу статьи** — «Следующая статья», а после последней — «Проверьте себя в итоговом тесте»: статьи читаются как последовательный курс.

## Доступность

- **Базовый уровень доступности, глубже не идём** — правильная разметка (кнопки — это кнопки, у полей есть подписи, вопрос связан с вариантами ответа), всё работает с клавиатуры, фокус не теряется после действий, итог обозначается не только цветом, тексты для экранного диктора — на русском там, где их всё равно озвучивает библиотека. Это почти ничего не стоит: такая разметка нужна и клавиатуре, и телефону. Не делаем: проверку настоящим экранным диктором (например, NVDA) и отдельные аудиты доступности — для учебного проекта это часы работы без заметной отдачи. Ориентир — стандарт WCAG. Для многих сайтов доступность обязательна по закону (в ЕС — Европейский акт о доступности; в России — для государственных сайтов, ориентир там — ГОСТ Р 52872-2019, основанный на WCAG), для этого проекта — нет.

## Типы упражнений

- **«Верно или неверно» — несколько утверждений в одной карточке (от 1 до 5, обычно 2–3)** — у каждого утверждения свой ответ и своё объяснение, балл — доля верно оценённых. Одно утверждение угадывается с вероятностью 50 %, несколько — уже нет, и частичный результат получается естественно. Карточка с 2–3 короткими утверждениями по размеру как один вопрос с выбором ответа; сколько упражнений ставить в статью, решается отдельно — при наполнении статей.
- **«Заполните пропуски» — свободный ввод с мягкой сверкой** — пользователь сам вспоминает слово, а это лучше закрепляет знание, чем выбор из готовых. При сверке не важны регистр, «ё/е», лишние пробелы и знаки препинания по краям; для каждого пропуска в банке хранится список допустимых форм слова («токен», «токены», «токенами»). Отвергнуты: выпадающий список (по сути — тот же выбор ответа) и банк слов для расстановки (проще, но слабее тренирует вспоминание). Балл — доля верно заполненных пропусков. Опечатки не засчитываются, но если ответ отличается от допустимого на одну букву (у слов от 8 букв — на две), подсказка просит проверить написание и форму слова (близкий ответ может быть и верным словом в другой форме — такие формы стоит добавлять в список); после раскрытия ответа эта подсказка не показывается; короткие слова (до 3 букв) не проверяются, чтобы не путать разные слова.
- **Фильтр нецензурной лексики не делаем** — введённый текст видит только сам пользователь, он не сохраняется и не показывается другим; любое постороннее слово и так засчитывается как неверный ответ. Фильтр понадобится, если появятся данные, которые видят другие пользователи (никнеймы, рейтинги).
- **«Расставьте шаги» — балл по тому, сколько шагов нужно переставить до верного порядка** — 0 перестановок — балл 1; максимально возможное число (порядок полностью обратный, n − 1 перестановок) — 0; между ними — пропорционально. Число перестановок — это шаги, не входящие в самую длинную цепочку уже верно упорядоченных шагов. Подсказка называет только это число: «Нужно переставить 1 шаг» — нейтрально, потому что после раскрытия ответа та же строка остаётся как итог. Отвергнуты: «доля шагов на своём месте» — несправедлива к сдвигам (один шаг, унесённый из начала в конец, обнуляет балл, хотя порядок почти верный); «доля верно упорядоченных пар шагов» — справедлива, но её трудно объяснить пользователю, а случайный порядок получает в среднем половину баллов. Список изначально перемешан, то есть ответ «заполнен» сразу; поэтому «Проверить» без единой перестановки ответ не проверяет, а показывает «Расставьте шаги в нужном порядке» — иначе баллы можно получить за чужую перестановку. Свойство выбранной оценки, принятое осознанно: 0 баллов («Неверно») бывает только при полностью обратном порядке, то есть итог «Неверно» сам подсказывает, что список нужно развернуть; на практике это почти не случается, а в тренажёре вреда нет. Шаги двигают перетаскиванием или кнопками «выше / ниже» (они же — способ для клавиатуры, поэтому перетаскивание с клавиатуры из библиотеки не подключено: его «пробел — взять» мешал бы нажатию кнопок); от 3 до 6 шагов; «Попробовать ещё раз» возвращает исходный порядок, как и в остальных типах. После раскрытия ответа у каждого шага отметка «Можно не трогать» или «Нужно переставить на место N» — отмеченных «переставить» ровно столько, сколько названо в подсказке. Место показывается только у шагов, которые нужно переставить: у остальных номер в верном порядке не совпадал бы с текущим (они встанут на место сами, когда переставят остальные) и только путал бы. Шаг тащат за левый блок с точками и номером, а не за всю карточку: иначе случайный сдвиг мыши при клике по тексту переставлял шаг незаметно для пользователя.
- **Состав типов: пять простых (выбор ответа, верно/неверно, пропуски, пары, порядок шагов) + собственный тип; сложные упражнения на применение навыка — решаем на итерации 5** — пары и порядок шагов проверяют то, что другим типам недоступно (связи между понятиями и последовательность действий), а простой тип на готовой оболочке обходится дешевле любого сложного. Если не хватит времени, урезаем сложные, а не простые.
- **Перетаскивание — библиотека `@dnd-kit` (классическая версия: `@dnd-kit/core`, для порядка шагов — `@dnd-kit/sortable`) и всегда запасной способ нажатиями** — библиотека сама обрабатывает мышь и палец, прокрутку страницы во время перетаскивания, умеет озвучивать действия для экранного диктора (тексты переведены на русский). Совместима с React 19. Последний выпуск — декабрь 2024: библиотека стабильна, но новых функций не будет. Отвергнуты: новая ветка `@dnd-kit/react` (версия 0.x, интерфейс ещё меняется, примеров мало); встроенный в браузер механизм перетаскивания и библиотеки на нём (Pragmatic drag-and-drop) — не работают с клавиатуры, неудобны на телефонах; упражнения совсем без перетаскивания — работают везде, но перетаскивание для пар и порядка шагов ожидается. Запасной способ обязателен по стандарту доступности WCAG 2.2 (п. 2.5.7): всё, что делается перетаскиванием, должно делаться и одиночными нажатиями — это удобнее на телефоне и работает с клавиатуры (Tab и Enter).
- **«Соедините пары» — пустые ячейки рядом с терминами и стопка определений под ними** — определение перетаскивают в ячейку или нажимают сначала определение, затем ячейку. Если ячейка занята, новая карточка встаёт в неё, а прежняя возвращается в стопку; карточку из ячейки можно вернуть в стопку. Пока заполнены не все ячейки, «Проверить» показывает «Заполните все пары» и подсвечивает пустые. Балл — доля верных пар. Почему не переставляемая колонка определений напротив терминов: с ячейками до начала работы нет случайных «бесплатных» совпадений, а пустая ячейка сама объясняет задачу. Почему стопка снизу, а не справа: колонка статьи узкая, определения — целые фразы; так одинаково на компьютере и на телефоне. Правило для вопросов: обычно 3–4 пары, 5–6 — только если по теме действительно столько терминов, чтобы не выбирать из них часть (банк допускает от 3 до 6; 2 пары не допускаются — первая пара сразу определяет вторую, а запрет порядка «как у терминов» оставил бы единственный порядок, то есть сам ответ): это учебный тренажёр, а не экзамен, длинные списки пар утомляют. Лишних определений-«обманок» нет — они не нужны. Порядок определений в стопке задаёт автор вопроса; при запуске банк проверяет только одно — что определения не идут в том же порядке, что и термины (защита от ошибки автора, пользователь эту проверку не видит). Более строгое правило «ни одно определение не стоит напротив своего термина» отвергнуто: оно само подсказывает ответ — при 3 парах из шести возможных порядков остаются два, при 4 — девять из 24.
