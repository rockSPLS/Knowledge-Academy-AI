# Журнал решений

Коротко: что решили и почему именно так, а не иначе. Основа для раздела README «Технологии и почему».

## Стек и инфраструктура

- **Next.js (App Router) + TypeScript** — фронтенд и бэкенд в одном проекте: один запуск и один деплой. App Router — актуальный подход Next.js с серверными компонентами.
- **Route Handlers (API внутри Next.js) вместо отдельного сервера** — бэкенду нужны проверка ответов и запросы к языковой модели, отдельный сервис был бы избыточен.
- **Tailwind CSS** — стили пишутся прямо в разметке, без отдельных CSS-файлов на каждый компонент; быстрее всего для небольшого проекта. Выбор подтверждён на шаге дизайна: отдельно изучать другие подходы к CSS (CSS-модули, обычный CSS) ради этого проекта нет смысла.
- **Деплой — Vercel** (тариф Hobby, https://prompt-eng-academy.vercel.app) — сайт пересобирается сам после каждого push, Next.js с серверной проверкой ответов (`/api/check`) работает без настройки: Vercel делает та же компания, что и Next.js. Отклонены: GitHub Pages — только статика, `/api/check` там не запустить, пришлось бы перенести ответы в браузер; Netlify и Cloudflare — риск несовместимости с новой версией Next.js; Render и Railway — бесплатный сервер «засыпает» и просыпается 30–60 с. Аналитику и Speed Insights от Vercel не подключаем (это сбор данных о посетителях), анонимная статистика сборки Next.js выключена переменной `NEXT_TELEMETRY_DISABLED` в настройках проекта на Vercel (в репозитории её нет).
- **`.gitattributes` с `text=auto`** — в репозитории LF, на машине разработчика окончания строк по его ОС (CRLF на Windows, LF на macOS).
- **Next.js 16.4.0 → 16.4.2 (и `eslint-config-next` 16.4.2) из-за уязвимостей октября 2026** — в 16.4.0 три уязвимости, исправленные в 16.4.1. Next.js советует обновиться всем, даже если сайт не использует уязвимые функции.
  - Уязвимости: GHSA-673q-mjm6-r5xr — выполнение чужого кода через функцию с `use cache`, которая возвращает несколько типизированных массивов; CVE-2026-96889 / GHSA-2464-fhr4-w9xw — выполнение чужого кода при оптимизации SVG-изображений библиотекой `sharp` на Linux с glibc; CVE-2026-94482 / GHSA-p3m5-59mp-jv5r — перегрузка сервера через Server Actions.
  - Наш сайт сейчас фактически не затронут: в коде нет ни `use cache`, ни Server Actions, а `sharp` уже исправленной версии 0.35.5. Обновляемся сразу, потому что `use cache` или Server Action могут появиться в следующих итерациях.
  - Выбрана 16.4.2, а не минимальная 16.4.1: сверх исправлений безопасности в ней только исправления Turbopack и документации, ломающих изменений нет. `react`/`react-dom` не меняем: исправление внутри Next.js.
  - Оставшиеся предупреждения `npm audit` (braces через линтер) касаются только разработки, на сайт не попадают. `npm audit fix --force` предлагает откатить `eslint-config-next` на версию 14 — это ломающее изменение, его не применяем.
  - Сообщение `SecurityFatalError` при сборке — встроенное напоминание Next.js об уязвимой версии (`experimental.agentUpgrade`, по умолчанию `security`): если сборку запускает ИИ-агент, первый запуск останавливается, повторный проходит. На исправленной версии его нет.

## Контент

- **Статьи в MDX** — текст остаётся обычным Markdown, а упражнение вставляется в любое место одной строкой `<Exercise id="..." />`. Альтернативы хуже: статьи на TSX неудобно редактировать как текст, хранение статей в JSON требует отдельного «рисовальщика» и неудобно для длинных текстов.
- **Единый банк вопросов** — каждый вопрос описан один раз и используется и в статье, и в итоговом тесте. Порядок банка — порядок курса, в этом порядке вопросы идут в тесте. Цена: прошедший статьи встретит в тесте знакомые вопросы — принято осознанно, отдельные вопросы для теста — работа на потом.
- **Структура статьи** — 2–4 упражнения на статью, каждое сразу после раздела, который оно проверяет; обобщающее упражнение по всей статье — в конце, после «Главного»; в статье не меньше двух разных типов; две карточки подряд не ставим; «Цена выбора» — итоговое упражнение в конце курса. Проверка сразу после прочитанного закрепляет именно этот раздел, а карточки подряд превращают статью в тест. Сначала упражнений было 3 + 4 + 2 + 2 = 11 (все шесть типов) — в тесте не меньше десяти вопросов и без продвинутого упражнения; с продвинутым стало 3 + 4 + 3 + 2 = 12, все семь типов. Вариант «строго по два на статью» отклонён: в тесте оказалось бы 9 вопросов, и минимум в 10 зависел бы от продвинутого упражнения, которое тогда было под вопросом.
- **Продвинутые упражнения отложены** — сначала обязательное (контент, тест, README); продвинутое — только если останется время, отдельным коммитом. Сделано после основного — «Улучшите промпт» (см. «Типы упражнений»).

## Архитектура упражнений

- **Композиция «оболочка + начинка» вместо наследования** — общая оболочка (`ExerciseShell`) и общий хук (`useExercise`) отвечают за состояния, проверку и обратную связь; каждый тип реализует только свой способ ввода ответа. Один большой компонент с `switch` по типам разросся бы, полностью независимые компоненты дублировали бы логику.
- **Тестовый режим через React Context** — упражнение само определяет режим: внутри теста отправляет результат в общий контекст, в статье работает автономно. Альтернатива — передавать колбэк `onResult` каждому вопросу — тоже рабочая, но контекст удобнее, когда счёт и прогресс нужны сразу в нескольких местах (прогресс-бар, вопросы, сводка).
- **Состояние теста на `useReducer`, счёт вычисляется из результатов** — хранится только список результатов, а баллы и прогресс считаются из него; нет риска, что счёт разойдётся с ответами. До завершения теста каждое упражнение сообщает в контекст черновик — заполнен ли ответ и начат ли он (`useExercise` получает от типа текущий ответ); из черновиков вычисляются «Готово N из M», пропущенные и незаполненные вопросы. Отправку своего ответа упражнение регистрирует в контексте, и кнопка «Завершить тест» вызывает их все: тип упражнения не знает о тесте, а тест — о том, как устроен ответ каждого типа.

## Проверка ответов

- **Проверка на сервере (POST `/api/check`)** — правильные ответы и объяснения не попадают в браузер до раскрытия (когда и как ответ раскрывается — см. раздел «Обратная связь»), их нельзя подсмотреть в коде страницы. Цена — небольшая задержка и состояние «проверяю…».
- **Осознанно не закрыто: перебор ответов через API** — сервер проверки ничего не запоминает, поэтому ответ можно подобрать, отправляя варианты по очереди, а счёт теста считается в браузере. Закрывать не стали: у портала нет оценок, рейтингов и сертификатов, это тренажёр — кто перебирает ответы, обманывает только себя. Как закрыть, если понадобится честный зачёт: хранить попытки прохождения в базе данных, принимать один ответ на вопрос в рамках попытки и считать итоговый балл на сервере. Ограничение частоты запросов не решает проблему, а лишь замедляет перебор; оно нужно для другого — защиты от нагрузки и автоматических запросов (в планах развития).
- **Банк вопросов помечен `server-only`** — если случайно импортировать его в браузерный код, сборка упадёт.
- **Вопросы страницы получают напрямую, без GET-эндпоинта** — серверные компоненты читают банк сами и передают в браузер только публичную часть. Запрос к собственному API из серверного компонента — лишний сетевой круг, а при статической сборке он вообще не работает.
- **Валидация запросов через zod** — схема описывает ожидаемый формат ответа и одновременно даёт TypeScript-тип.
- **Сервер не доверяет присланному ответу** — интерфейс не даёт отправить неполный ответ, но запрос к API можно отправить и в обход страницы (из инструментов разработчика или программой). Поэтому сервер проверяет, что ответ подходит именно этому упражнению: все утверждения, пропуски, пары или шаги на месте, без повторов и посторонних id. Иначе — ошибка 400, и балл не считается: иначе можно было бы, например, получить «верно» за неполный список.
- **Безопасность пользовательского ввода** — введённый текст выводится только React-ом как обычный текст (React сам экранирует его, поэтому вставленный HTML или скрипт не выполнится); `dangerouslySetInnerHTML` с пользовательскими данными не используется. Сервер ввод не хранит и не возвращает в ответе — только сравнивает с допустимыми ответами; размеры и формат ограничены схемой zod. Правила на будущее, когда появятся база данных и данные, видимые другим пользователям: запросы к базе — только параметризованные: через построитель запросов или ORM (например, Kysely, Drizzle, Prisma), никакой склейки строк и никаких пользовательских данных в «сыром» SQL (`sql.raw` и аналоги) — защита от SQL-инъекций, пользовательский текст — только как текст, проверка ввода — на сервере.

## Оценка ответов

- **Балл — доля правильно выполненных элементов ответа (от 0 до 1)** — найденные верные варианты, верно соединённые пары, верно заполненные пропуски. Единый принцип для всех типов упражнений; тест просто складывает баллы. У порядка шагов «элемент» можно понимать по-разному — правило выбрано отдельно (см. «Расставьте шаги» в разделе «Типы упражнений»).
- **Три итога: «Верно» (1), «Частично верно» (между 0 и 1), «Неверно» (0)** — итог должен совпадать с начисленным баллом: если за ответ «2 из 3» начисляется 0,67, писать «Неверно» было бы противоречием. Кроме того, «частично верно» подсказывает, что делать дальше — искать упущенное, а не пересматривать подход целиком.
- **Вопросы с несколькими верными ответами: «выберите все подходящие» с невидимым лимитом** — отметить можно не больше вариантов, чем верных (N), но само N заранее не показывается; подсказка «Можно выбрать не больше N вариантов» появляется, только если упереться в лимит. Балл = найдено / N. Так стратегия «отметить всё» невозможна на уровне интерфейса, и штрафы не нужны. Пользователь при этом сам решает, сколько вариантов верны, — это ценнее для обучения, чем готовое «выберите три». Рассмотренные альтернативы: «всё или ничего» не отличает «почти верно» от «совсем мимо»; формулы со штрафом за лишние варианты либо слишком строги (один лишний обнуляет всё), либо сложны для объяснения пользователю; шкала по числу ошибок (как в ЕГЭ) награждает «отметить всё», если неверный вариант всего один; поштучная оценка вариантов даёт много баллов за «отметить всё», когда верных большинство.

## Обратная связь

- **В статье — ступенчато** — после первой проверки показываются итог и подсказка, которая помогает найти ошибку, но не называет ответ (например, «Найдено 2 из 3 верных вариантов»). Дальше на выбор: «Попробовать ещё раз» или «Показать ответ» — отметки у верно выбранных, лишних и пропущенных вариантов и объяснение. Неотмеченные неверные варианты остаются без отметки: отмечается только то, на что стоит обратить внимание, иначе разбор превращается в шум. При верном ответе объяснение показывается сразу. После верного ответа и после «Показать ответ» кнопок повтора нет: ответ уже известен, повторять нечего. Почему не «всё сразу»: объяснение фактически называет ответ, и повторная попытка после него теряет смысл; ступенчатая схема даёт подумать ещё раз, но не заставляет мучиться.
- **В тесте — одна кнопка «Завершить тест», итог и разбор в конце** (решение владельца после проверки на сайте) — у вопросов теста своих кнопок нет, ответы можно менять до самого завершения, как на экзамене. Внизу — счётчик «Готово N из M» и кнопка «Завершить тест»: если заполнено всё, ответы отправляются, в каждой карточке появляются итог и разбор, а внизу — сводка с общим счётом (на неё переходит фокус). Раньше у каждого вопроса была своя «Ответить» и ответ после неё не менялся — но если пройти тест, не нажимая её, ничего не происходило, пока не вернёшься и не нажмёшь у каждого вопроса. Кнопка «Завершить тест» не блокируется (как и «Проверить»): если заполнено не всё, по нажатию — сообщение «Ответьте на все вопросы: осталось N вопросов», незаполненные вопросы подсвечиваются («Ответьте на этот вопрос»), страница прокручивается к первому из них. Отклонено: неактивная кнопка с подсказкой при наведении — на телефоне наведения нет, а неактивная кнопка не говорит, какие вопросы пропущены. Пропущенные вопросы подсвечиваются и по ходу (решение владельца): если начали отвечать на вопрос, а выше остались незаполненные, у них подпись «Вы пропустили этот вопрос», а у начатых, но не законченных — «Ответ заполнен не полностью»; подсветка исчезает, когда вопрос заполнен. Подсветка конкретных пустых мест внутри вопроса (пропуска, пары, утверждения) в тесте не включается — только карточка целиком. Если часть ответов не отправилась (нет сети), у этих вопросов сообщение, а «Завершить тест» можно нажать ещё раз — отправятся только они. Тест длинный, поэтому в правом нижнем углу — круглые кнопки «наверх» (к началу теста) и «вниз» (к «Завершить тест», после завершения — к итогам) (решение владельца): «наверх» видна, когда страницу прокрутили, «вниз» — пока не дошли до конца. Тест — проверка себя, а учиться с повторами и подсказками — в статьях. Сначала было решено показывать полный разбор сразу после каждого вопроса (повтора нет — прятать ответ незачем), но тогда тест превращался в ещё одну тренировку, а разбор одного вопроса подсказывал ответы на похожие дальше по тесту. Сервер не менялся: ответ в тесте по-прежнему раскрывается сразу, его просто не показывают до конца теста. Вариант «только счёт, без разбора» отклонён — по нему не понять, где ошибся.
- **Раскрытие ответа решает сервер** — в запрос проверки добавлен флаг `reveal`. Правильные ответы, объяснение и разбор по вариантам приходят в браузер, только если ответ верный, если пользователь нажал «Показать ответ» или если это тест. Правило записано в одном месте для всех типов упражнений. «Показать ответ» повторно отправляет тот же ответ — так разбор («лишний», «пропущен») строится относительно того, что выбрал пользователь, и отдельный эндпоинт не нужен.
- **Пояснения к отдельным вариантам — необязательные** — короткий комментарий «почему этот вариант неверный» самая полезная форма обратной связи, но писать его к каждому варианту дорого. Поле необязательное, заполняется там, где ошибка типичная; показывается у лишних и пропущенных вариантов.
- **Итог и разбор обозначаются значком и словом, а не только цветом** — требование стандарта доступности WCAG: часть людей не различает красный и зелёный.
- **Подписи разбора в «Выборе ответа» зависят от числа верных ответов** (решение владельца) — если верных несколько: «Верно» / «Лишний» / «Пропущен»; если один: «Верно» / «Неверно» / «Верный ответ», цвета и значки те же. При одном ответе «лишний» и «пропущен» читались странно: эти слова рассчитаны на выбор нескольких вариантов. Отклонены: «Ваш ответ — неверно» (длинная подпись на телефоне сужает текст варианта) и зелёный «Верный ответ» (зелёный во всех типах значит «вы ответили верно», а янтарный — «пропущено»).

## Дизайн

- **Простой лаконичный стиль** — нейтральная основа (белый фон, серые рамки, один цвет-акцент). Упражнения — заметные карточки, но не «кричат». Нейтральная основа не будет спорить с яркими элементами, если позже появятся иллюстрации или элементы прогресса.
- **Дизайн-токены** — все цвета заданы переменными в одном месте (`app/globals.css`) и подключены к Tailwind как именованные цвета (`bg-surface`, `text-muted`, `bg-accent-fill`…). Компоненты не содержат «зашитых» цветов: тема и палитра меняются правкой одного файла.
- **Светлая тема по умолчанию + переключатель на тёмную** — выбор запоминается в браузере. Чтобы страница не мигала светлой при загрузке, тема выставляется маленьким скриптом в `<head>` до первой отрисовки (приём из руководства Next.js «Preventing flash before hydration»). Тему не берём из системных настроек: по умолчанию сайт задуман светлым. Подпись кнопки говорит, что сделает нажатие: «Включить тёмную тему» / «Включить светлую тему» (значок — луна или солнце). Раньше подпись всегда была «Тёмная тема» — для диктора это работало как переключатель «вкл/выкл», но всплывающая подсказка «Тёмная тема» при уже включённой тёмной теме читалась как противоречие. Смена темы — плавное растворение всей страницы целиком (View Transitions API, 0,3 с), без отстающих элементов; если в системе включено «уменьшить движение» или браузер не поддерживает эту технологию — мгновенно, но тоже целиком.
- **Акцент — индиго** — холодный цвет не спорит с цветами итогов (зелёный, янтарный, красный) и с тёплыми иллюстративными элементами, которые могут появиться позже. Зелёный, янтарный и красный используются только для итогов и разбора ответов. Индиго разделён на два токена: светлый — для ссылок, значков и рамок (читается на тёмном фоне), насыщенный — для заливки кнопок с белым текстом. Раньше в тёмной теме кнопки были светло-индиговыми с чёрным текстом: формально контраст проходил стандарт, но на деле читалось тяжело. При наведении в тёмной теме кнопка светлеет, а не темнеет.
- **Типы упражнений различаются значком и названием, а не цветом** — карточка у всех типов одинаковая. Если раскрасить типы, их цвета спорили бы с цветами итогов.
- **Шрифт Geist везде** — единообразно и лаконично; вариант со шрифтом с засечками для текста статей рассмотрен и отклонён.
- **Главная — оглавление курса** — заголовок «ИИ без магии: основы за четыре шага», под ним строка-лозунг цветом акцента «Понять → Не обмануться → Применить → Защитить себя», короткое вступление и карточки статей по порядку («Шаг 1 · Понять» … «Шаг 4 · Защитить себя») со значками темы. Значки, а не картинки: они в том же стиле, что и интерфейс, и работают в обеих темах. Значок занимает полосу слева на всю высоту карточки — у оглавления характер «каталога шагов». Для первой статьи выбран курсор: он передаёт её главную мысль — модель предсказывает следующее слово (варианты «мозг», «схема связей», «коробка» рассмотрены; «коробка» ближе к теме контекста и визуально похожа на значок статьи о структуре промпта). **Лозунг курса.** Слова лозунга и подписи шагов берутся из списка статей — одно место правки. Лозунг — на главной, а не в шапке: шапка повторяется на всех страницах и узкая, на телефоне лозунг теснил бы «Пройти тест». Строка текстом, а не плашками со стрелками: плашки выглядят как кнопки, хотя не нажимаются, и повторяют подписи карточек.
- **Кнопки выглядят как кнопки** — у всех активных кнопок курсор-«рука» (Tailwind 4 по умолчанию оставляет обычную стрелку). Главное действие — заполненная кнопка в цвете акцента («Проверить», «Пройти тест»). «Проверить» (в тесте — общая «Завершить тест») никогда не блокируется: если ответ заполнен не полностью, по клику появляется подсказка («Заполните все пропуски», «Оцените все утверждения», «Выберите хотя бы один вариант»), незаполненное подсвечивается индиго и получает фокус — заблокированная кнопка не объясняет, чего не хватает. В тесте подсвечивается карточка незаполненного вопроса целиком («Ответьте на этот вопрос» или «Ответ заполнен не полностью»), страница прокручивается к первому, фокус — на карточку, диктор называет вопрос. Второстепенные — кнопки, а не ссылки, и немного различаются: «Попробовать ещё раз» — на мягком индиго-фоне (подталкиваем сначала подумать ещё раз), «Показать ответ» — нейтральная, с рамкой.
- **Логотип — «Собеседники»: человек и ИИ разговаривают** — круглая голова человека контуром (глаза, улыбка) и квадратная голова ИИ заливкой (антенна, глаза-экраны, «пиксельная» улыбка: дружелюбный, но всё же машина), над человеком облачко «печатает…». Тема курса — разговор человека с моделью, а не устройство ИИ, поэтому знак про диалог. Один компонент (`components/layout/LogoMark.tsx`) для шапки и обложки превью: в шапке цвета из токенов темы (в тёмной теме знак светлее), на обложке — фиксированные. Для вкладки браузера (16 px) сюжетная картинка не читается, поэтому значок вкладки — тот же образ, сведённый к сути: полукруг и полуквадрат, по глазу (`app/icon.svg`); стандартный значок Next.js из шаблона удалён. Обложка превью (`app/opengraph-image.tsx`, 1200×630) — знак и название сайта, без тезисов: их и так показывает описание под картинкой. Все цвета — индиго из палитры сайта. Рассмотрены и отклонены: лицо наполовину человек, наполовину робот (в маленьком размере не читается; цветной вариант с тёплой «человеческой» половиной — слишком пёстро), мозг наполовину живой, наполовину нейросеть (самый частый образ ИИ и про устройство модели, а не про общение), `>_` (штамп командной строки — сайт приняли бы за программистский), монограмма PE (без смысла курса).
- **Описание сайта для превью ссылки** повторяет заголовок и лозунг главной («ИИ без магии: основы за четыре шага — понять, не обмануться, применить, защитить себя…»): мессенджеры и поисковики показывают не заголовок страницы, а служебное описание из метаданных.
- **Рамка фокуса — браузерная, своей нет** — она показывает, где курсор, и её видимость требует стандарт доступности; цвет задаёт браузер (на Windows часто цвет акцента системы, например янтарный). Рассматривалась своя рамка в индиго — одинаковая во всех браузерах и не совпадающая по цвету с итогом «Частично верно»; решено не делать: браузерная рамка привычна и заведомо заметна, а наша подсветка незаполненного поля (индиго) от неё и так отличается.
- **«Пройти тест» — в шапке на всех страницах; правая часть шапки — место для действий** — сейчас там тест и переключатель темы, позже может появиться индикатор прогресса.
- **Отдельная страница списка статей убрана** — список живёт на главной, адрес `/articles` перенаправляет туда. Редирект временный (307), а не постоянный (308): постоянный браузеры запоминают навсегда, и вернуть страницу потом было бы сложно.
- **Переход по курсу внизу статьи** — «Следующая статья», а после последней — «Проверьте себя в итоговом тесте»: статьи читаются как последовательный курс.

## Доступность

- **Базовый уровень доступности, глубже не идём** — правильная разметка (кнопки — это кнопки, у полей есть подписи, вопрос связан с вариантами ответа), всё работает с клавиатуры, фокус не теряется после действий, итог обозначается не только цветом, тексты для экранного диктора — на русском там, где их всё равно озвучивает библиотека. Это почти ничего не стоит: такая разметка нужна и клавиатуре, и телефону. Не делаем: проверку настоящим экранным диктором (например, NVDA) и отдельные аудиты доступности — для учебного проекта это часы работы без заметной отдачи. Ориентир — стандарт WCAG. Для многих сайтов доступность обязательна по закону (в ЕС — Европейский акт о доступности; в России — для государственных сайтов, ориентир там — ГОСТ Р 52872-2019, основанный на WCAG), для этого проекта — нет.

## Типы упражнений

- **Состав типов: пять простых (выбор ответа, верно/неверно, пропуски, пары, порядок шагов) + собственный тип; сложные упражнения на применение навыка — решаем после основного (см. «Продвинутые упражнения отложены»)** — пары и порядок шагов проверяют то, что другим типам недоступно (связи между понятиями и последовательность действий), а простой тип на готовой оболочке обходится дешевле любого сложного. Продвинутый тип сделан после основного — «Улучшите промпт» (последний пункт раздела).
- **Перетаскивание — библиотека `@dnd-kit` (классическая версия: `@dnd-kit/core`, для порядка шагов — `@dnd-kit/sortable`) и всегда запасной способ нажатиями** — библиотека сама обрабатывает мышь и палец, прокрутку страницы во время перетаскивания, умеет озвучивать действия для экранного диктора (тексты переведены на русский). Совместима с React 19. Последний выпуск — декабрь 2024: библиотека стабильна, но новых функций не будет. Отвергнуты: новая ветка `@dnd-kit/react` (версия 0.x, интерфейс ещё меняется, примеров мало); встроенный в браузер механизм перетаскивания и библиотеки на нём (Pragmatic drag-and-drop) — не работают с клавиатуры, неудобны на телефонах; упражнения совсем без перетаскивания — работают везде, но перетаскивание для пар и порядка шагов ожидается. Запасной способ обязателен по стандарту доступности WCAG 2.2 (п. 2.5.7): всё, что делается перетаскиванием, должно делаться и одиночными нажатиями — это удобнее на телефоне и работает с клавиатуры (Tab и Enter).
- **«Верно или неверно» — несколько утверждений в одной карточке (от 1 до 5, обычно 2–3)** — у каждого утверждения свой ответ и своё объяснение, балл — доля верно оценённых. Одно утверждение угадывается с вероятностью 50 %, несколько — уже нет, и частичный результат получается естественно. Карточка с 2–3 короткими утверждениями по размеру как один вопрос с выбором ответа; сколько упражнений ставить в статью, решается отдельно — при наполнении статей. На узком экране текст утверждения — на всю ширину, кнопки «Верно / Неверно» — под ним в одну строку (решение владельца после проверки на телефоне): рядом с кнопками текст сжимался в столбик.
- **«Заполните пропуски» — свободный ввод с мягкой сверкой** — пользователь сам вспоминает слово, а это лучше закрепляет знание, чем выбор из готовых. При сверке не важны регистр, «ё/е», лишние пробелы и знаки препинания по краям; для каждого пропуска в банке хранится список допустимых форм слова («токен», «токены», «токенами»). Отвергнуты: выпадающий список (по сути — тот же выбор ответа) и банк слов для расстановки (проще, но слабее тренирует вспоминание). Балл — доля верно заполненных пропусков. Опечатки не засчитываются, но если ответ отличается от допустимого на одну букву (у слов от 8 букв — на две), подсказка просит проверить написание и форму слова (близкий ответ может быть и верным словом в другой форме — такие формы стоит добавлять в список); после раскрытия ответа эта подсказка не показывается; короткие слова (до 3 букв) не проверяются, чтобы не путать разные слова.
- **Фильтр нецензурной лексики не делаем** — введённый текст видит только сам пользователь, он не сохраняется и не показывается другим; любое постороннее слово и так засчитывается как неверный ответ. Фильтр понадобится, если появятся данные, которые видят другие пользователи (никнеймы, рейтинги).
- **«Соедините пары» — пустые ячейки рядом с терминами и стопка определений под ними** — определение перетаскивают в ячейку или нажимают сначала определение, затем ячейку. Если ячейка занята, новая карточка встаёт в неё, а прежняя возвращается в стопку; карточку из ячейки можно вернуть в стопку. Пока заполнены не все ячейки, «Проверить» показывает «Заполните все пары» и подсвечивает пустые. Балл — доля верных пар. Почему не переставляемая колонка определений напротив терминов: с ячейками до начала работы нет случайных «бесплатных» совпадений, а пустая ячейка сама объясняет задачу. Почему стопка снизу, а не справа: колонка статьи узкая, определения — целые фразы; так одинаково на компьютере и на телефоне. Правило для вопросов: обычно 3–4 пары, 5–6 — только если по теме действительно столько терминов, чтобы не выбирать из них часть (банк допускает от 3 до 6; 2 пары не допускаются — первая пара сразу определяет вторую, а запрет порядка «как у терминов» оставил бы единственный порядок, то есть сам ответ): это учебный тренажёр, а не экзамен, длинные списки пар утомляют. Лишних определений-«обманок» нет — они не нужны. Порядок определений в стопке задаёт автор вопроса; при запуске банк проверяет только одно — что определения не идут в том же порядке, что и термины (защита от ошибки автора, пользователь эту проверку не видит). Более строгое правило «ни одно определение не стоит напротив своего термина» отвергнуто: оно само подсказывает ответ — при 3 парах из шести возможных порядков остаются два, при 4 — девять из 24.
- **«Расставьте шаги» — балл по тому, сколько шагов нужно переставить до верного порядка** — 0 перестановок — балл 1; максимально возможное число (порядок полностью обратный, n − 1 перестановок) — 0; между ними — пропорционально. Число перестановок — это шаги, не входящие в самую длинную цепочку уже верно упорядоченных шагов. Подсказка называет только это число: «Нужно переставить 1 шаг» — нейтрально, потому что после раскрытия ответа та же строка остаётся как итог. Отвергнуты: «доля шагов на своём месте» — несправедлива к сдвигам (один шаг, унесённый из начала в конец, обнуляет балл, хотя порядок почти верный); «доля верно упорядоченных пар шагов» — справедлива, но её трудно объяснить пользователю, а случайный порядок получает в среднем половину баллов. Список изначально перемешан, то есть ответ «заполнен» сразу; поэтому «Проверить» без единой перестановки ответ не проверяет, а показывает «Расставьте шаги в нужном порядке» — иначе баллы можно получить за чужую перестановку. Свойство выбранной оценки, принятое осознанно: 0 баллов («Неверно») бывает только при полностью обратном порядке, то есть итог «Неверно» сам подсказывает, что список нужно развернуть; на практике это почти не случается, а в тренажёре вреда нет. Шаги двигают перетаскиванием или кнопками «выше / ниже» (они же — способ для клавиатуры, поэтому перетаскивание с клавиатуры из библиотеки не подключено: его «пробел — взять» мешал бы нажатию кнопок); от 3 до 6 шагов; «Попробовать ещё раз» возвращает исходный порядок, как и в остальных типах. После раскрытия ответа у каждого шага отметка «Можно не трогать» или «Нужно переставить на место N» — отмеченных «переставить» ровно столько, сколько названо в подсказке. Место показывается только у шагов, которые нужно переставить: у остальных номер в верном порядке не совпадал бы с текущим (они встанут на место сами, когда переставят остальные) и только путал бы. Мышью шаг тащат за левый блок с точками и номером, а не за всю карточку: иначе случайный сдвиг мыши при клике по тексту переставлял шаг незаметно для пользователя. Пальцем — долгим нажатием в любом месте шага (решение владельца после проверки на телефоне): ручку на телефоне искали методом тыка, а долгое нажатие на текст выделяло его; долгое нажатие случайным не бывает, поэтому прежний довод к пальцу не относится. Выделение текста в шагах отключено на сенсорных экранах (мышью текст выделяется), в подсказке — «на телефоне — нажмите на шаг и удерживайте». Номер слева — текущее место шага; у шагов, которые пользователь двигал сам, подпись «было N» и рамка акцентом (решение владельца): раньше номер просто менялся, и было непонятно, переставлен шаг или нет. Подписываются только шаги, которые двигали сами, а не сдвинутые следом соседи: иначе после перетаскивания с 4-го места на 1-е рамку получили бы четыре шага и признак перестал бы отвечать на вопрос «что я переставила». Рассмотрены: исходный номер слева и текущее место между стрелками (два числа на карточке путаются, к концу номера слева идут вразнобой и похожи на подсказку), исходный номер серым между стрелками (без подписи неясно, что значит цифра).
- **Собственный тип — «Цена выбора»** (в коде — `costed-select`, компонент `CostedSelect`) — дана задача и вперемешку сведения с ценой в токенах; нужно собрать промпт, взяв нужное и не раздув его. Инструкция: «У каждого варианта есть цена в токенах. Выберите, что положить в промпт, — в конце покажем, сколько потрачено с пользой» — это условие задачи (оценят не только верные варианты), без подсказок про дубли. Тренирует главный навык работы с контекстом: хороший промпт — это отбор и сжатие, а не «вывалить всё»; лишнее отвлекает модель, нужное тонет среди «воды», запрос становится дольше и дороже.
  - **Название:** «Цена выбора» прямо говорит, что цена есть у каждого варианта, в том числе у нужного; не подсказывает ответ (отвергнутое «Соберите без лишнего» толкало отметать громоздкие варианты сразу, хотя пропустить нужное хуже, чем взять его длинную версию) и не обещает оценку, которой нет. В коде и в интерфейсе — одно и то же по смыслу: `costed-select` — «выбор с ценой» без лимита (в «budget» и «knapsack» заложен лимит, а его нет). Название описывает механику, а тексты (токены, промпт, модель) — тему портала: любое упражнение этого типа у нас — про промпт, поэтому единицу и подсказки в данные упражнения не выносили (это работа впрок); поле цены называется `cost`. Тип — для итоговых упражнений повышенной сложности; у такого упражнения в карточке метка «★ Задача со звёздочкой» (поле `starred`) — справа в строке типа, чтобы её не принимали за часть названия типа, со звёздочкой и текстом: без текста звёздочку принимали бы за кнопку «в избранное», а подсказка при наведении не работает на телефоне.
  - **Механика.** Лимита окна нет: счётчик показывает размер промпта, шкала — от размера «взять всё». У части сведений есть полная и краткая версии, они стоят вразброс как отдельные варианты (проверяется при запуске, что не рядом); можно отметить обе — тогда вторая станет дублем. Заметить это — проверка понимания.
  - **«Вода» в токенах:** всё взятое из «воды»; у нужного сведения — всё сверх цены его самой короткой версии (письма клиента целиком полезны ровно настолько, насколько их пересказ в одну фразу; если версия одна, она целиком полезная); вторая версия уже взятого сведения — целиком «вода».
  - **Балл** — по общему принципу, доля выполненных элементов: каждое нужное сведение (в любой версии); «ничего опасного не отдали» — если в упражнении есть опасное (пароль, личные данные); «не раздуто» — «воды» в промпте нет совсем: ни лишних сведений, ни дублей, ни длинной версии там, где есть краткая. Два последних элемента засчитываются, только если взято не меньше трёх четвертей нужных сведений — иначе «одна вода» или «одно нужное сведение» получали бы их бесплатно.
  - **Штраф за опасное:** каждый взятый опасный вариант отнимает ещё один элемент (балл — не ниже нуля). Отдать модели пароль или личные данные — не лишний вес, а вредное действие, и два таких варианта хуже одного; без штрафа «взять всё» получало 5 из 7, со штрафом — 3 из 7. В выборе ответа штрафов нет: там неверный вариант — ошибка знания, а здесь — действие с последствиями. За «воду» штрафа нет — её уже наказывает строгое правило «не раздуто». Порог «три четверти нужных» — договорный: «почти всё». Строгость «ни капли воды» — осознанная: это итоговая «задача со звёздочкой», и «Верно» означает чистый промпт; рассматривался порог «воды не больше четверти промпта», но тогда «Верно» ставилось рядом с отметкой «Вода», а опасное «разбавляло» долю воды. Пустой выбор не проверяется — подсказка «Выберите, что положить в промпт»; сервер его тоже отклоняет. Подсказка до раскрытия ответа называет только счётчик и общие проблемы: «Нужных сведений в промпте: 4 из 5», «В промпт попало то, что нельзя отдавать модели», «В промпте есть лишнее».
  - **Итог** показывается под вариантами, в блоке «Эффективность выбора» (шкала «Размер промпта» остаётся наверху и после раскрытия — решение владельца: сначала разбор по вариантам, потом вывод рядом с итогом проверки): в заголовке — сколько потрачено с пользой (в процентах), ниже — доли полезного, «воды» и опасного от размера промпта, цветом и подписями (проценты в сумме всегда дают 100). Пара «Цена выбора» в начале и «Эффективность выбора» в конце сама объясняет, чем тип отличается от выбора ответа. Эффективность считается только от набранного промпта (полезные токены ÷ размер промпта), поэтому 100 % бывает и у неполного промпта; чтобы это не вводило в заблуждение, в заголовке написано «с пользой — N % промпта», а под шкалой — полнота: «Доли считаются от набранного промпта. Нужных сведений в нём: X из Y». Отметки у вариантов: «Нужное», «Нужное, но есть короче», «Дубль», «Вода», «Нельзя отдавать модели», «Верно, что не взяли», «Пропущено»; у «воды» и дублей отметка нейтральная — это лишний вес, а не ошибка в фактах. «Пропущено» ставится у самой короткой версии пропущенного сведения; «Верно, что не взяли» — только когда этот элемент засчитан в балл. Id вариантов нейтральные (не «history-full» и «history-short»), чтобы по разметке страницы нельзя было понять, какие версии парные.
  - **Почему не выбор нескольких ответов:** оценка зависит от веса в токенах, а не только от отметок — полная версия нужного сведения засчитывается, но добавляет «воду»; у выбора ответа нет ни цены, ни состава.
  - **Почему не «собрать промпт из блоков»:** там тренируется структура промпта (роль, задача, контекст, формат — по ячейкам), здесь — экономия и отбор: ячеек нет, решение в том, что взять, в какой версии и чего не брать.
  - **Место:** первое упражнение — в конце последней статьи, «Безопасность», и в нём есть сведения из всех четырёх статей: письма клиента целиком или кратко (токены и контекст), «если сведений не хватает — не придумывай» (галлюцинации), факты, объём и тон (структура промпта), пароль и личные данные клиента (безопасность); к концу курса пройдены все темы. Только в итоговый тест не ставим — собственный тип должен работать и в статье. Цены в токенах условные, но правдоподобные по порядку величины (в русском тексте токен — примерно 2–4 символа): «письма целиком» — несколько последних писем, около 1200 токенов, абзац об истории компании — 250; короткие сведения в одну строку — 20–40. Сначала длинные варианты стоили 220 и 120 — после проверки владелец заметила, что по смыслу это слишком дёшево; с честными ценами одни письма занимают почти три четверти шкалы, и разница между «целиком» и «кратко» видна сразу.
  - **Рассмотрены и отклонены:** окно с жёстким лимитом (например, 180 токенов) — искусственно: у современных моделей окна большие, и настоящая причина не раздувать промпт — качество ответа, а не нехватка места; выбор из двух версий «или–или» — подсказывал бы, что версии про одно и то же; ценность у каждого фрагмента и балл по близости к лучшему набору — ценности выглядели бы произвольными; опасное только с предупреждением, без влияния на балл — урок слабее; названия «Бюджет контекста», «Контекстное окно», «Не раздувайте контекст» (звучит как совет к конкретной задаче, а не как тип), «Задача со звёздочкой» как название типа (это уровень сложности, а не механика — оставлена меткой итогового упражнения), «Соберите без лишнего», «Эффективность выбора» (это название итога, а не условия; так назван блок итога), «Цена ошибки» (платят не только за ошибки, настраивает брать меньше), «Оптимальность выбора», «Взвесьте и выберите», «Составьте варианты», «Попробуйте сами»; полное обобщение (единица и тексты в данных упражнения) — работа впрок. Другой кандидат на собственный тип — «Калибровка уверенности» — отложен до выбора продвинутого упражнения.
- **Продвинутый тип — «Улучшите промпт»** (в коде — `prompt-rewrite`, компонент `PromptRewrite`) — дана ситуация, слабый промпт и заготовленный неудачный ответ модели; пользователь сам переписывает промпт.
  - **Почему этот.** Продвинутые механики проверяют применение, а не узнавание: поиск фрагмента в тексте (hot text), ветвящийся сценарий, кейс, конструируемый ответ с проверкой по рубрике, сравнение двух вариантов, «предскажи ответ», симуляция. Выбран конструируемый ответ: человек не выбирает из готового, а пишет промпт сам — главный навык курса. Заодно это ответ на вопрос, как проверить свободный ответ без ИИ. Рассмотрены и отклонены: «Найдите галлюцинацию» — по механике близко к выбору ответа; «Калибровка уверенности» — дороже и больше спорных решений; симулятор с заготовленными ответами — нужен свой ответ на каждое сочетание уточнений.
  - **Проверка без ИИ — по рубрике.** Рубрика — признаки сильного промпта; признак — набор регулярных выражений, найден, если совпал хотя бы один. Балл — доля найденных признаков. Эвристики оценивают текст пользователя, а заготовленные тексты (неудачный ответ модели, образец сильного промпта) показывают разницу. Проверка языковой моделью отложена в планы: нужны ключ API, оплата запросов, защита от инъекции промпта в самом ответе пользователя, а оценка модели менее предсказуема.
  - **Сценарий — рецепт ужина** (слабый промпт «Предложи рецепт ужина», ответ модели — утка по-пекински с маринадом на ночь). Бытовая ситуация, где сразу видно, чего модель не знала; тема не отвлекает от промпта. Рассмотрены: «объясни, что такое инфляция» — сама тема сложная; объявление о субботнике и поздравление коллеге.
  - **Условие — жизненная ситуация без готовых фактов** (решение владельца): «Вы стоите перед открытой дверцей холодильника… Продуктов не так много, времени тоже, а одним из едоков будет маленький ребёнок — для него специи надо подбирать осторожнее. Подробности придумайте сами, как будто это ваш вечер». Сначала в условии были готовые факты (курица, рис, 30 минут, трое, ребёнок 6 лет) — и скопированное условие получало «Верно», ничего не добавив от себя. Из нескольких формулировок выбрана та, где нет слов, совпадающих с признаками («быстро», «острое», «семья»); последняя фраза — чтобы новичок не застрял на «а какие у меня продукты», при этом она не перечисляет, что добавить.
  - **Четыре признака, все требуют конкретики:** «Контекст: какие продукты есть» (названия продуктов, а не «холодильник»), «Контекст: сколько едоков и кто они» (число или возраст, а не «семья» и «ребёнок»), «Ограничения: время или запреты — конкретно» (минуты или запрет; «быстро» не считается), «Формат ответа». Сначала признаков было три (без формата — для рецепта он не главное, а меньше признаков — меньше ложных срабатываний), но после смены условия формат добавлен: это то, что человек должен добавить от себя, в условии его нет. Роль в рубрику не входит: в статье она «по желанию». Скопированное условие получает 0 из 4.
  - **Обратная связь — ступенчатая, как у остальных типов:** до раскрытия только число найденных признаков; после — чек-лист («Есть» / «Не нашли» и как добавить) и образец. Названия признаков в браузер до раскрытия не попадают — они подсказывали бы, что дописать.
  - **Поле пустое с подсказкой «Напишите улучшенный промпт», «Попробовать ещё раз» сохраняет текст** (в остальных типах ответ сбрасывается): смысл упражнения — дорабатывать свой промпт, а не писать заново. Сначала поле было заполнено слабым промптом, но он и так показан над полем — в поле он только дублировался и выглядел как подсказка, которую надо стирать (решение владельца после проверки). Скопировать исходный промпт и дописать — считается изменением. Без изменений промпт не проверяется — «Измените промпт».
  - **Самопроверка рубрики при запуске:** образец обязан пройти все признаки, а слабый промпт и условие задачи — ни одного (так копия условия гарантированно получает 0); иначе сборка остановится. Шаблоны дополнительно проверены на нескольких десятках формулировок: копия условия, «для трёх человек», «шестилетнего», «минут на 20», «на 19:00», «какие продукты понадобятся» (это не контекст), «лосось, брокколи и киноа» (список продуктов расширен — придуманные продукты должны засчитываться), «без заморочек» (общие слова — не ограничение), «тремя абзацами» и «с заголовками» (статья называет это форматом) и т. п.
  - **Ограничения, принятые осознанно:** шаблоны ищут слова, а не смысл — необычную формулировку проверка может не узнать, а набор ключевых слов без смысла наберёт баллы. Ответа модели на промпт пользователя нет — проверяется сам промпт; без ИИ настоящий ответ не получить, а заготовить ответы на любые промпты невозможно. В карточке об обоих ограничениях сказано прямо, чтобы не возникало ожидания рецепта (настоящий ответ модели — в планах развития вместе с проверкой языковой моделью); проверка прозрачна, по чек-листу видно, что не нашлось. Для тренажёра приемлемо.
  - **Место** — «Структура промпта», после «Чек-листа перед отправкой»: упражнение — применение этого чек-листа.

## Расширение: путешествие по знаниям

- **Минимальный объём первой версии расширения** — генерация путешествия, прохождение на время, свободные ответы с оценкой моделью, собственный тип упражнения, очки, серия верных ответов, достижения, компаньон прогресса и отчёт. Сначала — основа: генерация, прохождение и проверка ответов; геймификация и отчёт — после неё. Отложены (вернёмся к ним в соответствующих итерациях): сюжетная подача материала (9), отдельные компоненты для каждого вида свободного ответа (10), отчёт в PDF через отдельную библиотеку (14). Компаньон прогресса оставлен (решение владельца): без него геймификация сводится к счётчикам.
- **Режим без ключа** — если ключ модели не задан, модель недоступна или исчерпан бесплатный объём, проект всё равно запускается: статьи, упражнения и тест работают, а вместо генерации — понятное сообщение, что она сейчас недоступна. Так проект можно запустить и посмотреть без регистрации у провайдера. Отклонено: без ключа просто падать с ошибкой — тогда проект нельзя даже открыть.
- **Ключ — только на сервере** — в `.env.local` на машине разработчика (файлы `.env*` не попадают в репозиторий; исключение — только для образца `.env.example` без значений) и в переменных окружения на хостинге; без приставки `NEXT_PUBLIC_`, поэтому Next.js не передаёт его в браузер. Модуль вызова модели помечен `server-only`, как и банк вопросов: если случайно импортировать его в браузерный код, сборка упадёт. Запросы к модели прямо из браузера отклонены: ключ оказался бы в коде страницы, и его мог бы взять любой посетитель.
- **Защита запросов к модели: лимит частоты запросов, ограничение длины текста, предупреждение «не вставляйте личные данные»** (решение владельца) — запросы к модели идут от имени владельца ключа и расходуют его бесплатный объём, а введённые тексты обрабатывает внешний провайдер. Ограничение частоты, которое для проверки ответов (`/api/check`) было отложено в планы развития (см. «Проверка ответов»), для запросов к модели вводим сразу; `/api/check` пока остаётся без него. Вставленный текст — ещё и канал для инъекции промпта («игнорируй инструкции и…»), поэтому защита от неё нужна и при генерации, и при оценке свободных ответов.
- **Модуль вызова модели — библиотека AI SDK и совместимый с OpenAI протокол; адрес, ключ и модель задаются переменными окружения** (решение владельца) — проект не привязан к одному провайдеру: кто запускает его у себя, вписывает в `.env.local` адрес, ключ и модель своего провайдера; модель меняется одной настройкой. Значений по умолчанию в коде нет, все три настройки обязательны: в коде не упоминаются ни провайдер, ни модель, а что вписать — подсказывает образец `.env.example`. Ответ модели проверяется zod-схемой, как и запросы к `/api/check`: для сервера это такие же внешние данные. Повторы при временных сбоях, тайм-аут и разбор ошибок берёт на себя библиотека. Версия библиотеки — 6: версия 7 требует Node 22 и новее, а проект должен запускаться и на Node 20, который поддерживает Next.js 16. Отклонены: встроенный в библиотеку доступ к одному конкретному сервису — кода чуть меньше, но для другого провайдера пришлось бы править код; свой модуль на `fetch` — повторы, тайм-ауты и разбор ошибок пришлось бы писать и проверять самим.
- **Лимит частоты: «мягкий» счётчик в памяти сервера, правило лимита в Firewall Vercel и потолок расходов в кабинете сервиса модели** (решение владельца) — серверные функции на хостинге работают в нескольких экземплярах без общей памяти: каждый считает только свои запросы, а после перезапуска счёт начинается заново. Поэтому счётчик в коде приблизительный, зато работает везде — локально и у любого, кто запустит проект. Единый для всех экземпляров счётчик по IP даёт правило Firewall Vercel: оно отсекает лишние запросы ещё до вызова функции и настраивается в кабинете, без кода (подключаем при публикации). Главная защита от расходов — потолок в кабинете сервиса модели: после него запросы отклоняются (последний запрос может немного превысить сумму). Отклонено: внешнее хранилище (например, Redis) ради точного счётчика — новый сервис, регистрация и ещё один секрет, а IP-адреса посетителей уходили бы наружу.
- **Источник — тема или вставленный текст, без загрузки файлов** (решение владельца) — вставленного текста достаточно, чтобы пройти путешествие по любой статье; загрузка PDF или .docx потребовала бы извлечения текста на сервере, ещё одной библиотеки и отдельных лимитов размера.
- **Генерация в два шага: план, затем упражнения по чекпоинтам** (решение владельца) — первый запрос к модели разбирает материал и составляет план: чекпоинты с понятием, конспектом, ключевыми фактами, типичными заблуждениями, зависимостями и типами упражнений. Затем на каждый чекпоинт — отдельный запрос за упражнениями, все параллельно: по времени генерация занимает примерно два запроса подряд. Второй шаг получает не весь текст пользователя, а карточку чекпоинта из первого: запрос короче, а вставленный текст (через него возможна инъекция промпта) видит только первый шаг. Сбой в одном чекпоинте переделывается отдельно; если чекпоинт не получился и после повтора, остальные запросы отменяются — путешествия всё равно не будет, а бесплатный объём модели тратился бы впустую. По той же причине запросы отменяются, если посетитель закрыл страницу, не дождавшись путешествия. Отклонено: всё путешествие одним запросом — длинный ответ может оборваться по лимиту длины, к концу качество падает, а любая ошибка — переделка целиком.
- **Чекпоинт — одно понятие и 2–3 упражнения разных типов, в путешествии 3–5 чекпоинтов** (решение владельца) — понятие (термин, закономерность, причина и следствие, процесс) можно проверить отдельно, и ошибка говорит конкретно: «не понято вот это». Отдельный факт — слишком мелко, вопросы превращаются в угадайки; раздел текста — слишком крупно, в нём несколько понятий, и по ошибке не видно, какое не понято. Всего 6–15 упражнений; если понятий в материале больше, модель выбирает главные, а остальное включает фактами в них — десять чекпоинтов растянули бы прохождение на полчаса и дольше.
- **Порядок — по зависимостям, сложность растёт** (решение владельца) — модель указывает, на какие более ранние чекпоинты опирается понятие (сервер проверяет, что ссылки только назад). У каждого упражнения уровень сложности: 1 — понять и узнать, 2 — объяснить и различить, 3 — применить в новой ситуации (уровень пригодится таймеру). Внутри чекпоинта сервер ставит упражнения по возрастанию сложности: сначала «понял ли», потом «умеешь ли применить»; дальние чекпоинты в целом сложнее.
- **Неочевидные вопросы и правдоподобные неверные варианты** (решение владельца) — промпт требует проверять понимание и применение (ситуации, «что будет, если», отличие от похожего), а не узнавание фраз. Неверные варианты строятся из типичных заблуждений, которые первый шаг выписывает для каждого понятия; запрещены «всё перечисленное», шуточные варианты, подсказка в вопросе и верный вариант заметно длиннее остальных.
- **Вопрос «Выбора ответа» задаёт столько ответов, сколько верных вариантов — правило в промпте, без проверки на сервере** (решение владельца) — сгенерированный вопрос «В каких из перечисленных ситуаций…» звучал так, будто верных несколько, а верный был один, и подпись «Выберите один ответ» спорила с вопросом. Правило сформулировано по смыслу, а не по грамматике: при одном верном вопрос такой, что правильный ответ может быть только один (что произойдёт, почему, что лучше всего объясняет); при нескольких — вопрос прямо говорит, что верных несколько, но не называет их число («Выберите все…», а не «Какие два…»): число верных интерфейс заранее не показывает. Отклонено: ещё и проверка на сервере — по смыслу текста её надёжно не сделать, можно поймать лишь грубые признаки по словам («каких», «какие из»); такая проверка отклоняла бы и нормальные вопросы, а каждый отказ — лишний запрос к модели, при повторном отказе — несостоявшееся путешествие.
- **Разнообразие типов** (решение владельца) — модель выбирает типы под понятие (порядок шагов — только для процессов, пары — когда есть хотя бы три однородных элемента); сервер требует разные типы внутри чекпоинта и не меньше трёх типов во всём путешествии. Сначала генерировались только базовые типы: выбор ответа, верно/неверно, пропуски, пары, порядок шагов; позже добавились свободные ответы и калибровка уверенности.
- **Подсказка к каждому упражнению** (решение владельца) — наводит на ход мысли, но не называет ответ. Хранится вместе с правильными ответами и открывается по запросу; когда она становится доступна — решаем вместе с прохождением, сколько стоит в очках — вместе с геймификацией.
- **Конспект в каждом чекпоинте** (решение владельца) — 3–6 предложений о понятии. Если человек ввёл только тему, читать ему нечего: без конспекта путешествие лишь проверяло бы то, что он и так знает. В начале путешествия он выбирает: сначала изучить или сразу проверить себя (как это выглядит — решаем вместе с прохождением).
- **Как снижаем риск неправды в конспекте и упражнениях** (решение владельца) — по тексту модель опирается только на него; по теме — только на устоявшиеся сведения, без неуверенных цифр, дат и имён, а тему без надёжных сведений (свежие новости, слухи) отклоняет. Если в присланном тексте есть утверждения, которые расходятся с общепринятыми сведениями, первый шаг отмечает до трёх таких утверждений с пояснением; промпты обоих шагов запрещают делать их верными ответами (проверить это кодом нельзя — это вопрос смысла), а путешествие показывает их с пометкой «проверьте» — не «ложь», а «расходится»: модель тоже может ошибаться. В интерфейсе — пометка, что конспект и вопросы составлены ИИ. Отдельный запрос на проверку фактов не делаем: проверяет такая же модель, ловит лишь часть ошибок, а генерация дольше и дороже примерно на треть.
- **Содержание пишет модель, устройство — сервер** — модель возвращает только тексты и признаки верности; id и порядок показа вариантов, утверждений, определений и шагов задаёт сервер, перемешивая их. Так id не выдают ответ (у шагов они идут по порядку показа, а не по верному порядку), а верный вариант не стоит всегда первым, куда его обычно ставит модель.
- **Проверка сгенерированного — та же, что у банка, плюс правила генерации; при ошибке — один повтор** — ответ модели проверяется zod-схемой, затем правилами генерации (число чекпоинтов и упражнений, типы, зависимости, длина текстов) и той же функцией `validateExercise`, что упражнения банка при запуске. Если не прошло, шаг повторяется один раз, и модель получает текст ошибки: «нужно от 3 до 6 пар» исправить проще, чем угадать. Не помогло — понятная ошибка «Модель ответила некорректно. Попробуйте ещё раз». Схема для модели описывает только форму ответа, без ограничений длины и числа элементов: такие схемы принимают провайдеры со строгим режимом структурированного ответа, а содержание сервер проверяет сам — с понятным текстом ошибки.
- **Защита от инъекции промпта при генерации** — текст пользователя передаётся модели между метками со случайной частью, поэтому «закрыть» блок изнутри и дописать свои инструкции нельзя; системный промпт говорит, что внутри — материал, а не команды; ответ ограничен схемой и проверками, инструментов у модели нет. Второй шаг текста пользователя не видит, но карточка чекпоинта — это ответ модели по этому тексту, поэтому она тоже передаётся между такими метками. Даже если инъекция удастся, её результат увидит только тот, кто вставил текст.
- **Хранение: зашифрованное путешествие в браузере, без базы данных** (решение владельца) — серверные функции не помнят ничего между запросами, а правильные ответы, как и в первой версии портала, не должны попадать в браузер до раскрытия. Сервер шифрует путешествие целиком (с ответами и подсказками) и отдаёт браузеру вместе с публичной частью; при проверке ответа браузер присылает зашифрованное путешествие обратно, сервер расшифровывает его и проверяет ответ. Прочитать ответы без ключа нельзя, подмена любого байта обнаруживается: AES-256-GCM — шифрование с проверкой подлинности, встроенный в Node модуль `crypto`, без новой библиотеки. Этот приём руководство Next.js по аутентификации называет «stateless sessions»; отличие — строка идёт в теле запроса, а не в cookie: в cookie помещается около 4 КБ, а путешествие больше. Цена: секретный ключ `JOURNEY_SECRET` на машине разработчика и в настройках хостинга (без него генерация недоступна); смена ключа делает выданные путешествия недействительными; путешествие живёт в браузере, и на другом устройстве его не продолжить. Ответы и прогресс прохождения тоже хранятся в браузере. Отклонено: база данных — путешествие открывалось бы по ссылке с любого устройства, но это новый сервис и секрет, а тексты пользователей хранились бы у третьей стороны. Счётчику лимита база тоже не нужна — он остаётся, как решено выше.
- **Ключ лимита для IPv6 — сеть /64; размер запроса проверяется до чтения** — абонент IPv6 обычно получает целую сеть /64 и может менять адрес внутри неё, поэтому лимит считается по сети, а не по адресу (IPv4 — по адресу). Слишком большой запрос к модели отклоняется по заголовку Content-Length, не читая тело; если заголовка нет, чтение обрывается, как только размер превышен.
- **Путешествие — отдельная страница «Путешествие»; кнопка в шапке, приглашение вверху главной** (решение владельца) — путешествие — самостоятельный раздел со своим прохождением, а не часть статьи или теста; на главной приглашение стоит над оглавлением курса, чтобы новую возможность было видно сразу. Страница ведёт человека по шагам: форма → старт → (конспекты) → чекпоинты → конец путешествия.
- **Упражнения чекпоинта показываются все сразу, под липкой полосой времени** (решение владельца) — видно, сколько работы, и время чекпоинта легко распределить между 2–3 упражнениями; раскладка знакома по статьям. Отклонено: по одному упражнению на экране — на телефоне компактнее, но при общем таймере чекпоинта хуже видно, сколько осталось.
- **Две попытки на упражнение, за вторую — понижающий коэффициент; у «верно/неверно» — одна** (решение владельца) — ошибку человек исправляет сам, это полезнее для запоминания, а время на вторую попытку тратится из того же таймера. Ответ проверяется сразу; после неудачной первой попытки — «Попробовать ещё раз» или «Показать ответ», как в статьях; правильный ответ раскрывается после второй попытки или по кнопке. Номер попытки запоминается, коэффициент задаём вместе с очками. В «верно/неверно» вторая попытка бессмысленна: если всё оценено неверно, верный ответ получается переворотом всех оценок, а при частично верном — угадыванием, какое утверждение ошибочно. Отклонено: одна попытка у всех типов — проще, но без шанса исправиться.
- **Подсказка — по кнопке в упражнении, доступна сразу** (решение владельца) — человек сам решает, когда помощь нужна; цена в очках (вместе с геймификацией) удержит от того, чтобы открывать её всегда. Открытая подсказка остаётся видна и после ответа. Отклонены: подсказка только после ошибки — человек сначала пробует сам, но помощь, которую он хотел бы раньше, недоступна; через N секунд без ответа — таймер и так подгоняет, а «застрял» не отличить от «читает длинный вопрос», и подсказка открывалась бы без просьбы.
- **Таймер — свой на каждый чекпоинт; время — сумма норм упражнений; полоса индиго → янтарный → красный** (решение владельца) — норма упражнения: время на вопрос плюс время на каждый элемент ответа (вариант, утверждение, пропуск, пару, шаг), умноженное на коэффициент сложности (1; 1,3; 1,6); время чекпоинта округляется вверх до 15 секунд. Время идёт только во время упражнений: конспекты, итог чекпоинта и переход между чекпоинтами — без таймера. Когда время вышло, ответы отправляются как есть: заполненный ответ проверяется, после неудачной первой попытки засчитывается она, а незаполненный получает «Время вышло — ответа нет» (0 баллов) и общее объяснение; путешествие идёт дальше. Полоса меньше чем на половине времени становится янтарной, последние 10 секунд — красной и пульсирует (если человек не просил уменьшить движение); звука нет. Зелёный не используется: в первой версии он закреплён за итогом «Верно», и зелёная полоса читалась бы как «верно». Экранному диктору время объявляется на порогах, а не каждую секунду. Оставшееся время чекпоинта запоминается — за него будут бонусные очки. Отклонено: один таймер на всё путешествие — гибче, но к концу длинного путешествия время сжимается, а бонус считается один раз за всё.
- **«Сначала изучить» — все конспекты одной страницей, затем проверка** (решение владельца) — конспекты идут в порядке маршрута, с заголовками чекпоинтов, поэтому порядок от простого к сложному сохраняется; это 15–30 предложений, примерно одна короткая статья. Проверка честнее: отвечаешь не по только что прочитанному абзацу. Во время проверки конспекты не видны и открываются в итоге своего чекпоинта; в режиме «сразу проверить» конспект впервые показывается там же, раскрытым. Отклонено: конспект перед каждым чекпоинтом — связка «прочитал → сразу проверил», но проверяется кратковременная память.
- **Прогресс прохождения — в localStorage браузера; таймер хранит момент окончания, а не остаток** — перезагрузка страницы возвращает туда же, где человек остановился, а заново составлять путешествие (это снова запросы к модели) не нужно. Остаток времени каждый раз вычисляется как «момент окончания минус сейчас», поэтому перезагрузка или переход на другую вкладку не дают лишнего времени. Ответы, которые ещё не отправлены, при перезагрузке теряются; упражнения с итогом показываются итогом и объяснением. «Новое путешествие» до конца прохождения спрашивает подтверждение. Ограничение, принятое осознанно: если открыть путешествие в двух вкладках, они перезаписывают прогресс друг друга (сохраняется то, что записано последним); синхронизация вкладок — лишний код ради редкого случая.
- **Проверка ответов путешествия — отдельный маршрут, то же правило раскрытия** — браузер присылает зашифрованное путешествие и id упражнения, сервер его расшифровывает и проверяет ответ той же `checkAnswer`, что у банка: разбор с правильными ответами — только при верном ответе или явном раскрытии. Тот же маршрут отдаёт подсказку и, если ответа не было, общее объяснение. Свой лимит размера запроса — 400 КБ: зашифрованное путешествие бывает до ~270 КБ, а обычный лимит рассчитан на текст для генерации. Лимита частоты нет, как и у `/api/check`: модель здесь не вызывается (кроме оценки свободных ответов, которые появились позже, — у неё свой лимит, см. ниже).
- **Свободный ответ — четыре вида задания: общая начинка и по компоненту на вид** (решение владельца) — виды: развёрнутый ответ, «объясните простыми словами», «объясните другу», «приведите свой пример». Поле, отправка, оценка и отзыв — в одном общем компоненте; каждый вид — свой небольшой компонент с названием, значком, инструкцией и подсказкой в поле, как типы упражнений внутри общей оболочки (композиция). Виды различаются заданием и одним критерием: «простыми словами» — термины не используются или пояснены; «другу» — друг верит в типичное заблуждение из плана, и его нужно разобрать; «свой пример» — пример свой, конкретный и действительно показывает понятие. К этому вопросу вернулись в итерации 10 (при планировании его отложили). Отклонены: один компонент с режимами — кода чуть меньше, но вида не видно в коде; четыре самостоятельных компонента — повторяли бы одну и ту же логику.
- **Критерии — 2–3 на вопрос, создаются вместе с ним; каждый «выполнен / не выполнен»; балл — доля выполненных** (решение владельца) — так же, как у остальных типов (доля верных элементов): 2 из 3 — «Частично верно». Критерии, как и правильные ответы, хранятся в зашифрованном путешествии. Модель решает только «да / нет» по каждому критерию и указывает номер критерия — по номеру сервер сопоставляет отзыв с критерием, даже если модель переставит их местами (решение владельца); балл считает сервер. Критерий — главная мысль, без которой ответ неверен или неполон, а не второстепенная деталь: числа, даты и отдельные факты — только если вопрос прямо о них. Иначе верное объяснение сути своими словами получало бы «Частично» (так было на первой пробе генерации). Отклонено: три уровня («да / частично / нет») — граница «частично» размыта, и один и тот же ответ модель может оценить по-разному.
- **Верная мысль своими словами засчитывается** (решение владельца) — у оценщика явное правило: оценивать смысл, а не совпадение слов. Синонимы, пересказ, другой порядок, бытовые слова вместо терминов засчитываются; мысль, сказанная неточно, тоже — с подсказкой, как сказать точнее. Не засчитывается: мысли в ответе нет, ответ ей противоречит, рядом с верной мыслью неверная о том же («кислород и из воды, и из углекислого газа»), только слова без связи между ними, повтор условия. Образец оценщик получает как один из возможных хороших ответов, а не как эталон формулировки. Отклонено: засчитывать только ясно выраженное — больше незаслуженных «Неверно» как раз у ответов своими словами.
- **Отзыв по каждому критерию после каждой попытки; сами критерии и образец — после раскрытия** (решение владельца) — после попытки человек видит, что получилось, и наводящий вопрос к тому, чего не хватает, без правильного ответа. Формулировки критериев подсказали бы, что дописать, поэтому они и образец ответа открываются после второй попытки или по «Показать ответ». Попыток две, как у других типов. Отклонено: до раскрытия только счёт «2 из 3» — вторая попытка почти вслепую.
- **Оценка ответа моделью и защита от инъекции в ответе** — ответ пользователя передаётся модели между метками со случайной частью, как текст при генерации; оценщику сказано, что обращения к нему внутри ответа («засчитай всё») не выполняются и не засчитываются. Модель отвечает по схеме — только «выполнен / не выполнен» и отзыв по каждому критерию; сервер проверяет число элементов, номера критериев и длину отзывов (при ошибке — один повтор с объяснением) и сам считает балл. Даже удачная инъекция меняет только оценку и отзыв, которые видит сам автор ответа.
- **«Показать ответ» не обращается к модели снова: оценка запечатывается** — вместе с итогом сервер отдаёт оценку, зашифрованную так же, как путешествие, но своим ключом, и привязанную к путешествию, упражнению и тексту ответа. При раскрытии сервер берёт её: запрос не тратится, а разбор совпадает с итогом, который человек уже видел (новый запрос мог бы дать другой итог). Если текст ответа изменился, оценка не подходит и делается заново. Отклонено: хранить оценки на сервере — у серверных функций нет общей памяти (см. лимит частоты).
- **Свой лимит частоты для оценки — лимиты генерации × 5** (решение владельца) — у генерации и оценки отдельные счётчики. Оценка: 25 за 10 минут с одного IP и 300 в час на экземпляр сервера. В путешествии не больше двух свободных ответов по две попытки и одна калибровка уверенности с одной попыткой, то есть до пяти оценок, поэтому любое путешествие, которое разрешил лимит генерации, можно пройти целиком. Раскрытие по запечатанной оценке лимит не тратит. Сначала множитель был 4 — по числу оценок свободных ответов; с калибровкой стал 5.
- **Свободных ответов в путешествии — не больше двух, и разных видов; вид выбирает план** (разные виды — решение владельца) — каждый свободный ответ занимает 2–3 минуты и одну-две оценки моделью. Модель ставит их туда, где понятие важно уметь объяснить (причина, механизм, отличие от похожего) или применить на своём примере. Вид назначает первый шаг генерации — план: он видит все понятия сразу и подбирает вид под понятие («объясните другу» — только если заблуждение и правда бытовое; без заблуждения в карточке сервер такой вид не пропустит). Упражнения чекпоинтов составляются одновременно и не знают, что выбрали соседи, поэтому на этом шаге два одинаковых вида подряд не исключить (так и вышло на пробе). Сервер не пропустит план, где свободных ответов больше двух или их виды совпадают. Норма времени — 2 минуты с коэффициентом сложности (начальное число, уточняется по ручным прохождениям).
- **Если оценить ответ нельзя, путешествие не застревает** — без ключа, при недоступной модели или после лимита карточка говорит, что оценка сейчас недоступна, и предлагает попробовать ещё раз или «Пропустить без оценки»: открываются объяснение и образец, упражнение не засчитывается (если первая попытка уже была — засчитана она). Если время чекпоинта вышло, а оценить ответ не удалось, это происходит само.
- **Оценщик для «Улучшите промпт» в статьях не подключаем** (решение владельца) — там проверка по признакам без ИИ, и она работает в статьях и итоговом тесте без ключа. Оценщику понадобились бы лимит частоты, ожидание ответа модели и запасной путь без ключа в общей проверке ответов и в тесте. Пункт — в планах развития.
- **Собственный тип путешествий — «Калибровка уверенности» с ответами своими словами** (решение владельца; в коде — `calibration`, компонент `Calibration`) — 3–4 коротких вопроса по понятию, на каждый человек отвечает своими словами (хватит слова или фразы) и отмечает «Точно знаю» или «Сомневаюсь». Ответы оценивает ИИ, а в конце карточки — вывод «Когда вы были уверены, вы были правы в N из M (%)». Упражнение показывает то, чего не видно в остальных типах: где человек уверен, что знает, а на деле ошибается. Оценивается и знание, и самооценка. Пример: «Почему лист выглядит зелёным?» — «хлорофилл поглощает зелёный свет» · «Точно знаю» — это уверенная ошибка. Отклонены: утверждения «верно / неверно» с отметкой уверенности (первый вариант) — там угадываешь в половине случаев, поэтому «Сомневаюсь» мало что значит, и проверяется узнавание, а не вспоминание; «Разложите по группам» — привычный тип, близкий к «Соедините пары»; «Задайте вопрос, который проверяет понимание» — ещё один свободный текст, трудный для новичка. В первой версии портала «Калибровку» откладывали как более дорогую (см. «Типы упражнений»); оценщик ответов, который появился вместе со свободными ответами, сделал её открытую версию возможной.
- **Шкала уверенности — два уровня; очки за вопрос: 1 / 0,5 / 0 / −1** (решение владельца) — «Точно знаю» и верно — 1, «Сомневаюсь» и верно — 0,5, «Сомневаюсь» и неверно — 0, «Точно знаю» и неверно — −1. Балл — сумма очков, делённая на число вопросов, не ниже нуля; итог — по баллу, как во всех типах. Так честная отметка выгоднее всего: «Точно знаю» приносит больше, только если вы правы чаще, чем в двух случаях из трёх; блеф «всегда точно знаю» проигрывает на ошибках, вечное «сомневаюсь» даёт не больше половины. Если все ответы верны, но в части вы сомневались, итог — «Частично верно», и подсказка говорит это прямо («Все ответы верны, но в 2 из 4 вы сомневались»): неуверенное знание стоит меньше — в этом смысл метода (оценка с учётом уверенности, certainty-based marking, из медицинского образования). Отклонено: три уровня («Наугад / Скорее / Точно знаю», очки 0,33 / 0,67 / 1 и 0 / −0,67 / −2, как в исходном методе) — на телефоне пять кнопок на вопрос, неясно, какие уровни считать уверенными для вывода, а одна уверенная ошибка стирает два верных ответа.
- **Калибровка — ровно одна в каждом путешествии, во втором чекпоинте или в первом** (решение владельца) — так тип виден в любом путешествии, а вывод и связанные с ним очки (серия, достижение за точную самооценку) доступны всегда; до второго чекпоинта доходит и тот, кто проходит путешествие не до конца. План ставит её во второй чекпоинт, а в первый — если у второго понятия нет типичных заблуждений или там нужен «Верно или неверно»: первый чекпоинт самый простой, уверенно ошибиться в нём труднее. Сервер не пропустит план, где калибровок не одна, где она дальше второго чекпоинта или где у её чекпоинта нет заблуждений — вопросы строятся на них. Отклонены: от 0 до 2 на выбор плана — в части путешествий типа не было бы вовсе; любой чекпоинт, где больше заблуждений (первый вариант), — калибровка могла оказаться в четвёртом или пятом, и тот, кто бросил путешествие раньше, её бы не увидел. Вместе с «Верно или неверно» в один чекпоинт не ставим: оба проверяют, верно ли сказанное, — это повтор (решение агента); в разных чекпоинтах они встречаются.
- **Попытка одна, разбор сразу; уверенность оценщик не видит** — после разбора отметка уверенности уже не честная, а вторая попытка свелась бы к исправлению по подсказкам; так же одна попытка у «Верно или неверно». Оценщик получает вопросы, правильные ответы и ответы человека, каждый в своих метках (защита от инъекции, как у свободного ответа), но не отметки уверенности — они не должны влиять на «верно или нет». Модель решает по каждому вопросу «верно / неверно» и пишет одно предложение; балл считает сервер. Без модели — тот же запасной путь, что у свободного ответа: «Пропустить без оценки», откроются правильные ответы.
- **Короткий ответ — норма** (по вопросу владельца: не сочтёт ли ИИ ответ в одно слово слишком узким) — генерация пишет только вопросы с однозначным коротким ответом: что, из чего, почему (одной причиной), как называется; без «да или нет», без выбора из двух названных вариантов (их угадывают) и без «объясните подробно». Хотя бы половина вопросов — на типичные заблуждения, где легко уверенно ошибиться. Оценщику сказано прямо: слово или фраза с сутью — верный ответ, развёрнутости не требовать. Проверено на настоящей модели: ответы в одно слово («световой», «АТФ», «глюкоза», «устьица») засчитаны, «крахмал» вместо «глюкоза» — нет, с пояснением, обращение к оценщику в ответе не сработало. Задание в карточке одно для всех путешествий — его задаёт сервер: «Ответьте своими словами — хватит фразы — и отметьте, насколько уверены» (формулировка владельца).
- **Разбор калибровки — сочетание уверенности и верности** — у каждого вопроса одна из четырёх отметок: «Верно, и вы были уверены», «Верно — вы знали больше, чем думали», «Неверно — и вы сомневались не зря», «Уверенная ошибка» (отдельный значок предупреждения); отзыв ИИ, у неверных — правильный ответ. Под вопросами — вывод: доля верных среди уверенных ответов, сколько было сомнений и сколько из них верных, и одна фраза — что делать (уверенные ошибки перепроверить). В итоге упражнения сохраняются пары «уверенность — верно ли» по каждому вопросу, а вывод и будущие очки считаются из них.
- **Разбор промптов: признаки, по которым ответ угадывается без знания темы, названы поимённо; пример «плохо → хорошо»** (решение владельца) — независимая оценка промптов на настоящих ответах модели показала, что общего правила «неверные варианты правдоподобны, верный не длиннее» мало. Категоричные слова («всего лишь», «сразу же», «полностью») стояли почти только в неверных утверждениях, верный вариант повторял слова вопроса, пары находились по синонимам и грамматике, шаги — по словам «впервые», «затем». Теперь промпт перечисляет эти признаки — общие и для каждого типа упражнений, а короткий пример на «Фотосинтезе» показывает плохие варианты и исправленные; модели сказано, что пример показывает только приём: вопросы и варианты из него не копировать, тему и факты брать только из карточки (так пример не мешает и путешествию по самому «Фотосинтезу»). Часть признаков (категоричные слова в неверных утверждениях, слово-категория в начале определений) встречается и после правок — вернёмся к ним при выборе модели для опубликованного сайта. Отклонено: серверная проверка длины верного варианта — ловит один признак из многих, а каждый отказ — лишний запрос к модели. Строку самопроверки в конце промпта («мог бы решить тот, кто не знает темы?») пробовали и убрали (решение владельца): пользы в прогонах не видно, а рассуждающая модель и так проверяет себя в скрытом черновике.
- **Подсказка — следующий шаг рассуждения, а не напоминание факта** — правило «наводит на ход мысли или напоминает нужный факт» давало подсказки, которые выдают ответ (5 из 11 настоящих подсказок к «Выбору ответа»): у вопроса на вспоминание нужный факт и есть ответ. Теперь подсказка говорит, на что посмотреть в условии или какую мысль конспекта применить, без слов верного ответа и без «X или Y?». Подсказка будет стоить очков — она не должна покупать ответ.
- **Поле «что проверяет» у каждого упражнения** (решение владельца) — упражнения одного чекпоинта повторяли друг друга: один и тот же вопрос в «Выборе ответа» и в калибровке. Теперь модель первым полем пишет, какой факт или заблуждение проверяет упражнение, и у упражнений чекпоинта эти поля не совпадают; в путешествие поле не попадает. Дословные повторы пропали, пересечения по теме остались: в чекпоинте одно понятие и 3–6 фактов, а калибровка одна берёт 3–4 вопроса. Это известное ограничение; сильнее помог бы план, который раздаёт факты по упражнениям, — отложено. Сначала пробовали только правило в промпте (решение владельца) — повторы остались во всех прогонах.
- **Ученик видит только конспект: слова «карточка» в текстах для него нет** — шаг упражнений получает данные чекпоинта под названием «карточка», и слово попадало к ученику: «не берите примеры из карточки», «в карточке ничего не говорится о…». Промпт объясняет, что ученик видит только конспект, и разрешает ссылаться на конспект, только если нужное в нём есть. Критерий своего примера — «не пример из вопроса»: ни карточки, ни конспекта оценщик не видит, и проверить остальное не может.
- **Критерий отвечает только на то, о чём спрашивает вопрос** — критерий «сказано, что память формируется и после прививки, и после болезни» повторял условие вопроса, а оценщику велено не засчитывать повтор условия: верный ответ получил бы «не выполнен». Теперь критерий не требует ни того, что уже сказано в вопросе, ни того, о чём вопрос не просит.
- **Сомнительное утверждение текста — только пометка, своего исправления модель не дописывает** (решение владельца; уточняет «Как снижаем риск неправды…») — исправляя «дрожжи лучше всего работают при 70 °C», модель вписала в конспект свои цифры (25–30 °C), которых нет в тексте, и построила на них упражнения. Даже верные, такие сведения нарушают правило «по тексту — только текст», а пометки «проверьте» у них нет. Объяснение, что не так с утверждением, остаётся в самой пометке. Отклонено: разрешить общепринятое исправление без точных цифр — полезнее, но открывает дорогу непомеченным сведениям модели.
- **«Выбор ответа» — не больше чем в половине чекпоинтов** — описание типа «подходит почти всегда» приводило к «Выбору ответа» в каждом чекпоинте. Правило только в промпте; сервер по-прежнему требует разные типы в чекпоинте и не меньше трёх во всём путешествии.
- **Отзыв оценщика начинается с сути, а не со «Верно»** — итог («Есть» / «Не хватает», «Верно» / «Неверно») интерфейс показывает рядом, и «Верно: …» в отзыве его повторяло. Правило теперь одно у обоих оценщиков; если модель всё же начнёт с «Верно:», сервер убирает это начало.
- **Промпт упражнений — целиком, а не только разделы нужных типов** (решение владельца) — сборка из нужных разделов сократила бы запрос примерно на 700 токенов из 3–4 тысяч, но промпт перестал бы быть одним текстом, который можно прочитать и объяснить, а экономия в деньгах невелика: дороже всего ответ модели, а одинаковое начало промпта у всех запросов сервис модели кэширует, и оно обходится дешевле.
- **Уровень размышлений модели — необязательная настройка `AI_REASONING_EFFORT`** (решение владельца) — рассуждающая модель перед ответом пишет скрытый черновик. С более длинными правилами он вырос примерно вдвое и иногда съедал весь лимит длины ответа — генерация обрывалась. С уровнем `low` генерация «Фотосинтеза» прошла за 37 секунд вместо 60–100 и без сбоев, качество на глаз не хуже. Настройка действует на все запросы к модели, и на оценку ответов тоже (проверено: оценки верные, отзывы по делу, 2–14 секунд). Настройка необязательная: не задана — параметр не отправляется, потому что не все модели его принимают, а проект должен работать с любым провайдером. Отклонено: всегда `low` в коде — с моделью, которая параметр не принимает, генерация перестала бы работать.
- **Пустой ответ модели — повтор, а не «модель недоступна»** — если черновик съел весь лимит, модель возвращает ответ без текста. Раньше это считалось недоступностью модели, и генерация сразу прекращалась; теперь это ответ не по схеме, и шаг генерации или оценка ответа повторяется один раз, как при других ошибках ответа.
