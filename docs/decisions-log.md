# Журнал решений

Коротко: что решили и почему именно так, а не иначе. Основа для раздела README «Технологии и решения».

## Стек и инфраструктура

- **Next.js (App Router) + TypeScript** — фронтенд и бэкенд в одном проекте: один запуск и один деплой. App Router — актуальный подход Next.js с серверными компонентами.
- **Route Handlers (API внутри Next.js) вместо отдельного сервера** — бэкенду нужна одна задача (проверка ответов), отдельный сервис был бы избыточен.
- **Tailwind CSS** — стили пишутся прямо в разметке, без отдельных CSS-файлов на каждый компонент; быстрее всего для небольшого проекта.
- **`.gitattributes` с `text=auto`** — в репозитории LF, на машине разработчика окончания строк по его ОС (CRLF на Windows, LF на macOS).

## Контент

- **Статьи в MDX** — текст остаётся обычным Markdown, а упражнение вставляется в любое место одной строкой `<Exercise id="..." />`. Альтернативы хуже: статьи на TSX неудобно редактировать как текст, хранение статей в JSON требует отдельного «рисовальщика» и неудобно для длинных текстов.
- **Единый банк вопросов** — каждый вопрос описан один раз и используется и в статье, и в итоговом тесте.

## Архитектура упражнений

- **Композиция «оболочка + начинка» вместо наследования** — общая оболочка (`ExerciseShell`) и общий хук (`useExercise`) отвечают за состояния, проверку и обратную связь; каждый тип реализует только свой способ ввода ответа. Один большой компонент с `switch` по типам разросся бы, полностью независимые компоненты дублировали бы логику.
- **Тестовый режим через React Context** — упражнение само определяет режим: внутри теста отправляет результат в общий контекст, в статье работает автономно. Альтернатива — передавать колбэк `onResult` каждому вопросу — тоже рабочая, но контекст удобнее, когда счёт и прогресс нужны сразу в нескольких местах (прогресс-бар, вопросы, сводка).
- **Состояние теста на `useReducer`, счёт вычисляется из результатов** — хранится только список результатов, а баллы и прогресс считаются из него; нет риска, что счёт разойдётся с ответами.

## Проверка ответов

- **Проверка на сервере (POST `/api/check`)** — правильные ответы и объяснения не попадают в браузер, их нельзя подсмотреть в коде страницы. Цена — небольшая задержка и состояние «проверяю…».
- **Осознанно не закрыто: перебор ответов через API** — сервер проверки ничего не запоминает, поэтому ответ можно подобрать, отправляя варианты по очереди, а счёт теста считается в браузере. Закрывать не стали: у портала нет оценок, рейтингов и сертификатов, это тренажёр — кто перебирает ответы, обманывает только себя. Как закрыть, если понадобится честный зачёт: хранить попытки прохождения в базе данных, принимать один ответ на вопрос в рамках попытки и считать итоговый балл на сервере. Ограничение частоты запросов не решает проблему, а лишь замедляет перебор.
- **Банк вопросов помечен `server-only`** — если случайно импортировать его в браузерный код, сборка упадёт.
- **Вопросы страницы получают напрямую, без GET-эндпоинта** — серверные компоненты читают банк сами и передают в браузер только публичную часть. Запрос к собственному API из серверного компонента — лишний сетевой круг, а при статической сборке он вообще не работает.
- **Валидация запросов через zod** — схема описывает ожидаемый формат ответа и одновременно даёт TypeScript-тип.

## Оценка ответов

- **Балл — доля правильно выполненных элементов ответа (от 0 до 1)** — найденные верные варианты, верно соединённые пары, верно заполненные пропуски. Единый принцип для всех типов упражнений; тест просто складывает баллы. Для упражнения на порядок шагов правило будет выбрано отдельно — там «элемент» можно понимать по-разному.
- **Три итога: «Верно» (1), «Частично верно» (между 0 и 1), «Неверно» (0)** — итог должен совпадать с начисленным баллом: если за ответ «2 из 3» начисляется 0,67, писать «Неверно» было бы противоречием. Кроме того, «частично верно» подсказывает, что делать дальше — искать упущенное, а не пересматривать подход целиком.
- **Вопросы с несколькими верными ответами: «выберите все подходящие» с невидимым лимитом** — отметить можно не больше вариантов, чем верных (N), но само N заранее не показывается; подсказка «Можно выбрать не больше N вариантов» появляется, только если упереться в лимит. Балл = найдено / N. Так стратегия «отметить всё» невозможна на уровне интерфейса, и штрафы не нужны. Пользователь при этом сам решает, сколько вариантов верны, — это ценнее для обучения, чем готовое «выберите три». Рассмотренные альтернативы: «всё или ничего» не отличает «почти верно» от «совсем мимо»; формулы со штрафом за лишние варианты либо слишком строги (один лишний обнуляет всё), либо сложны для объяснения пользователю; шкала по числу ошибок (как в ЕГЭ) награждает «отметить всё», если неверный вариант всего один; поштучная оценка вариантов даёт много баллов за «отметить всё», когда верных большинство.
